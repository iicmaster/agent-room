# PRD Quality Review — Agent Room v0.2 — Networked Cross-Session Chat for AI Agents (rev 2026-09-20)

Re-gate: this review judges the revised PRD (`prd.md`, updated 2026-09-20) and its `addendum.md` decision record D1–D19 as they stand. Calibration: solo-builder developer product (MCP plugin + self-hostable server), personal tool first, chain-top (feeds architecture → epics & stories).

## Overall verdict

Green-light for architecture and epic drafting after one high-severity fix. The D13–D19 revision did its job: identity, delivery, guarantee lanes, and lifecycle semantics are pinned as decisions with honest limitation statements, and every FR carries testable consequences with numeric bounds. Residual risk is concentrated in small interaction gaps between otherwise fully-specified FRs — the FR-10 hold matrix has no row for the receiving installation's own Actor (breaking the flagship D14 path in Remote Mode under a literal reading), offline Chat-ID resolution is ambiguous, and the free-space gates ship without an FR home — plus a stale addendum §3 that contradicts the very decisions it accompanies.

## Decision-readiness — strong

The revision converted open tension into decisions with their semantics fixed, and the PRD body states them as decisions, not considerations. D13 pins collision behavior ("refused with an explicit error ... no silent suffixing"), rename semantics ("never rewrites history"), and the trust split ("trust binds keys, never names"); D14 demotes the Broadcast Room to "the secondary commons" and builds the harder surface first; FR-16 states a rejection inside the requirement itself ("Content-based duplicate dropping is deliberately absent (rejected alternative, addendum D18)"). Limitations are surfaced where a smoother PRD would hedge: FR-7 "no confidentiality is claimed against the host operator in v0.2"; FR-16 "abuse floors for an invite-only realm, not a volumetric-DoS guarantee"; §1 "a hypothesis about where the product can live, not validated demand." The trade-off ledger is real — §6 Non-Goals and addendum §2 name what was given up (push delivery, federation, at-rest encryption, content dedup, single global server) and why.

The single remaining Open Question (§9: Chat ID normalization details) is genuinely open, correctly gated ("confirm or adjust before epics"), and pre-covered by FR-19's assumption with concrete values — the right shape for a pre-epic gate, not a rhetorical question.

### Findings
- **low** v0.2 claimed-client matrix never named (§5 NFR-2, §8 SM-1) — NFR-2 makes "each release smoke-tests ... every client it claims — and claims no client it has not smoke-tested" a hard release gate, and SM-1 requires "two client vendors" without naming them; UJ-1 implies Claude Code + Zcode, but the PRD never states the v0.2 claimed-client list, so the conformance/release epic has no concrete matrix to gate against. *Fix:* one line in NFR-2 or §7.1 naming the v0.2 claimed clients (at minimum Claude Code and Zcode, per UJ-1/SM-1).

## Substance over theater — strong

No persona furniture: §2 is jobs-to-be-done shaped for a solo builder, with a Non-Users subsection doing real work (SSO/teams, open registration, human chat). The NFRs are the opposite of boilerplate — every one carries product-specific thresholds: NFR-5 "p95 ≤150 ms (excluding network RTT)", NFR-6 with 5-minute RSS/FD sampling windows and a four-hour monotonic-growth criterion, NFR-8 a complete wire-version contract down to error codes and rejection semantics. The Vision is non-swappable ("the open rooms layer for agents that no vendor owns," grounded in a specific landscape gap and immediately hedged as a hypothesis). The Gate taxonomy (§3) exists to keep honesty labels straight, and the FRs use it against themselves — FR-9: "the PRD never presents it as enforced security." Positioning restraint per D19 ("one portable package is claimed only in the clients a release actually smoke-tests") replaces the earlier marketing claim. Nothing here reads as furniture.

The thesis is explicit and the features serve it: local-first default with cross-machine/cross-vendor as the opt-in "killing feature," DM-first. Prioritization follows the thesis rather than ease — Direct Rooms (the harder surface) are primary and built first per D14, and SM-1 "leads with a DM exchange." Success metrics validate the thesis rather than measure activity: SM-1 is the cross-everything milestone, SM-2/SM-3 are continuity protocols (named as first-class by D10, matching JTBD 4), and SM-4 is the honest solo-tool bar ("does not abandon it"). Scope kind is platform/problem-solving for a developer tool, and the scope logic matches it: gates ship day one (D7), built open-ready (D8). This does not read as a backlog with headings.

## Done-ness clarity — strong

This is the dimension the revision improved most. Every FR carries a "Consequences (testable)" block with numbers: FR-8's page bound 1–200 and 20 s server hold; FR-14's token format (`ar_inv1_` + 43 base64url chars), single-transaction consume, and "5/minute/source-IP, burst 5"; FR-13's soak pass criteria; FR-18's 5 s freshness bound. Outcomes are enumerated, not adjectival — FR-17 names six send statuses; FR-20 defines the lost-response resolution discipline end to end. Non-functional sections give bounds, not adjectives (NFR-4/5/6/8). There is no "handles gracefully," no "reasonable performance," no "user-friendly" anywhere in the FR surface.

Two interaction gaps between otherwise fully-specified FRs are the only places an engineer must guess, and one of them sits on the flagship path — fix it before epics. Both are single-clause fixes, which is why the dimension still earns strong; neither is vagueness, each is a missing row in an otherwise complete matrix.

### Findings
- **high** FR-10 hold matrix has no row for the receiving installation's own Actor (§4.3 FR-10 vs §3 Glossary "Held Message", addendum D14) — the Glossary defines a Held Message as "a message from a sender outside the receiving installation's per-Realm Allowlist," and FR-10's default matrix auto-delivers only "Local Mode same-OS-user senders" or "Remote allowlisted Actors," holding "any other Remote sender — including one claiming to be on the same machine." Literal reading: an installation configured for a Remote server whose second terminal DMs the first — the D14 first-class path ("two terminals of one machine DM each other"), routed through the remote realm — is held, because nothing states that a sender provably using the receiving installation's own Identity Key delivers automatically. Unlike third-party same-machine claims, this case is mechanically verifiable (sender fingerprint == the plugin's own key). *Fix:* add a matrix row — sender Actor key == receiving installation's key ⇒ always deliver, both modes — and note in FR-10's consequences that self-recognition is by local fingerprint comparison, the one same-machine claim that is verifiable.
- **medium** Opening a DM by Chat ID is ambiguous when two offline Actors last held the same name (§4.3 FR-21 vs §4.1 FR-19, §4.2 FR-5) — FR-19 enforces Chat ID uniqueness only "among currently-connected Sessions on that Server," so names are freed at disconnect; FR-21's `room_direct_open({chat_id})` "resolves an enrolled peer — offline peers included," but when two different offline Actors both last-used "bob," no rule says which pair room opens. This bites the primary surface in exactly the offline case the PRD deliberately supports. *Fix:* one consequence line on FR-21: ambiguous offline resolution refuses with a disambiguating list (key fingerprint + last-seen per candidate), never silently picks one.
- **low** `outcome_unknown` attributed to the wrong speaker (§4.5 FR-17 vs §4.4 FR-20) — FR-17 opens "The Server returns actionable statuses for every send: ... and `outcome_unknown` for a request whose outcome the client could not observe," but a request whose outcome the client could not observe has by definition no delivered server response; FR-20 states it correctly ("The client surfaces this as `outcome_unknown → resolved-by-retry`"). An API implementer cutting stories from FR-17 alone would look for a wire code that cannot exist. *Fix:* reword FR-17 to five server-returned statuses plus the client-side resolution state defined in FR-20.
- **low** Client-side cursor keying is not realm-qualified (§4.4 FR-20, §3 "Seq Cursor") — cursors persist "per (installation, room)" while §6 allows server switching ("switching servers is manual configuration") and the Glossary's Realm permits one installation to hold relationships with several Realms. If room IDs are not globally unique across realms, cursors and the plugin's room list can collide after a switch; NFR-7's idempotency tuple has the same room-scoping question (harmless server-side, live client-side). *Fix:* state the rule — room IDs are realm-scoped and all client-side per-room state (cursors, held cache) keys on (realm, room) — or declare room IDs globally unique.

## Scope honesty — strong

Seven explicit Non-Goals plus a five-item Out of Scope. Omissions that could be silently assumed are called out at the point of assumption: DMs invisible to the operator viewer (FR-7 assumption), "no identity recovery in v0.2" (FR-3), plaintext at rest "stated openly" (§6), the viewer excluding Direct Rooms. The `[NOTE FOR PM]` sits at a real deferred decision (capacity quotas before broad sharing), not a safe checkpoint. Open-items density is right for a green-light PRD: one Open Question, four inline `[ASSUMPTION]` tags, one NOTE FOR PM. De-scoping is done audibly, not silently — D14 explicitly supersedes a D13 sub-decision on the record ("superseding the self-DM refusal briefly written under D13") rather than dropping it down a memory hole.

## Downstream usability — adequate

The extraction skeleton is excellent: a 19-term glossary that FR text actually uses; FR/UJ/SM IDs complete, unique, and bidirectionally cross-referenced (every FR names its UJs; every UJ is realized; NFR-1–NFR-8 all exist and are referenced); each FR section makes sense pulled out alone. Two hazards keep this from strong, and both will produce wrong downstream artifacts if not fixed: a shipped behavior whose citation dangles inside the PRD proper, and a stale addendum section that the addendum's own header routes to architecture.

### Findings
- **medium** Free-space gates ship without an FR home, cited to sections that don't contain them (§7.1 vs §4.4 FR-11, §5 NFR-7, §7.2 NOTE, §4.5 FR-17) — §7.1 claims "storage free-space gates and operator capacity visibility (FR-11/NFR-7, operator guide)," but FR-11 (restart survival) and NFR-7 (data semantics) contain no thresholds. The actual spec — "warn <1 GiB, refuse appends <256 MiB with storage_low" — lives only in §7.2's `[NOTE FOR PM]` and addendum D15(4), while `storage_low` appears as a sender status in FR-17. An epic writer extracting from §7.1 gets a citation that resolves to nothing; the backup guide of D15(4) has no PRD mention at all; and "operator guide" is a deliverable that appears nowhere else (FR-4 defines a "deployment guide"). *Fix:* put the free-space thresholds and `storage_low` trigger into FR-17's consequences (or a small FR-22), fold backup/monitoring guidance into FR-4's deployment-guide consequence, and fix the §7.1 citation.
- **medium** Addendum §3 mechanism notes contradict the decision log they accompany (addendum §3.1, §3.3 vs D16–D18, §4.3 FR-16, §4.3 FR-8) — §3.1's guarantee table still specifies "Rate limit / duplicate drop | Server | per-key counters; byte-identical window dedupe" although D18 rejected content deduplication and FR-16 states it is "deliberately absent"; §3.1 keeps the two-lane "Client" taxonomy and "key↔handle binding" that D17/D13 replaced with Plugin-enforced/Instructed and Chat ID/Actor; §3.3 says sequences are "server-local" where D16/FR-8 fixed them "room-local." The addendum's header says it holds "depth that belongs downstream (architecture, solution design)" — an architect skimming §3.1 can reintroduce a rejected alternative or the wrong sequence namespace. *Fix:* refresh §3.1/§3.3 to post-D13–D19 vocabulary and decisions, or stamp both "(pre-D13 seed; superseded — see D13–D19)".

## Shape fit — strong

Correct shape for a solo-builder developer product feeding architecture and stories: a capability spec with exactly the UJ density that earns its keep — four UJs, role protagonists (Builder, server operator) carrying context inline, each load-bearing in both directions. SMs are operational protocols (a kill/restore drill, a soak, dated usage notes) rather than user-facing growth metrics — right for an internal/solo tool, and the counter-metrics are operational too. The NFR depth (wire versioning, gate lanes, endurance budgets) is earned by the near-rebuild of a shipped v0.1 with an open-realm security surface, not template rigor. Not over-formalized, not under-formalized.
