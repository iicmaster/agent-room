## Intent

**Problem:** `docs/epics.md:395-405` (Story 3.3) requires held messages to expose metadata only, with nothing ever lost. FR-10 (`docs/prds/prd-agent-room-2026-09-20/prd.md:193-201`) fixes the metadata set — realm, sender Chat ID, Actor key fingerprint, room, sequence, time, size, held count, no body text — and the recovery rule: the 100-entry held cap bounds a local listing/cache, overflow is explicit and recoverable from the durable log, and recovery never depends on the cache (point read `after_seq = seq − 1`, `limit = 1`); eviction never deletes, approves, or permanently skips. FR-20 (`:242-248`) makes ingestion a separate, human-gated state from transport: held messages still advance the read cursor. Story 3.2 (`server/client/trust.mjs`) produces held rows (body withheld behind a marker, `held`/`held_reason` recorded) but nothing consumes them: there is no held state, no held count, no recovery, no release, no human-preview substrate, and no proof that the cursor and held state stay out of each other's way.

**Approach:** one plugin-layer slice on top of 3.2's held rows. (1) `server/client/held.mjs` (new) owns the per-realm held pipeline at `PLUGIN_DATA/realms/<realm_id>/held.json` (0600, atomic writes, the cursor/allowlist machinery's discipline: missing/corrupt degrades to the empty default, malformed rows are dropped not surfaced, unsafe realm keys are coded refusals, and the read bound is a derived constant). Each record is keyed (realm, room, seq) and carries the metadata (sender chat id, fingerprint, room, seq, time, size, reason, registered_at) plus a BOUNDED body cache — at most `HELD_CACHE_MAX` (100) body copies, drop-oldest by caching time; eviction drops only the cached BODY COPY, so the record (and the held listing) survives forever until an explicit human release. The API splits by audience: `heldList`/`heldCount` project a fixed whitelist (the agent-visible shape — realm, chat id, fingerprint, room, seq, time, size, reason — built field-by-field so the body copy is structurally absent), while `heldBody` (cached copy, else point read `after_seq = seq − 1, limit = 1` through an injected api-client seam, byte-identical to the cached artifact) and `heldClear` (release: the record and its preview reference go away; no auto-approve exists) are human-surface functions. Read-modify-write cycles serialize through a per-realm promise chain, the cursor chain's discipline. (2) The MCP adapter registers every held row a read produces — the RAW pre-matrix rows paired index-for-index with their matrix reasons — AFTER the cursor persists, so a held seq is consumed like any other (FR-20), a registration failure can never block the consumed page, and a cursor failure can never lose the held record; registration failures surface as an additive note, never a failed read. (3) Two additive tools join the surface — `room_held_list {room_id?}` (metadata-only list with the realm-wide held count) and `room_held_count {}` — with closed schemas; the adapter never imports the body paths, so no agent-reachable code path can carry or release a held body. (4) The proof: `tests/held.test.mjs` (new) in the house style — real server children, real MCP children, the real api-client for point-read recovery, literal oracles — plus the 3.3 evidence entry, a dated additive AD-12 amendment, and this spec.

## Boundaries & Constraints

**Always:** keep the metadata-only guarantee STRUCTURAL — `heldMetadataRow` is a whitelist projection that builds the agent-visible row from a fixed field list, so the body copy, its caching time, and the registration bookkeeping are absent by construction, and no downstream filter can regress; keep the two audiences separate by import graph — the tool layer gets `heldList`/`heldCount`/`registerHeldMessages` only, and `heldBody`/`heldClear` stay unreachable from it (the test scans the adapter's source for their names); make eviction bound only the body cache — drop the oldest cached_at copies past `HELD_CACHE_MAX`, keep every record metadata-complete, never delete/approve/skip, and let the listing exceed the cap (the cap bounds the cache, not the truth); make recovery cache-independent — the point read is exactly `after_seq = seq − 1, limit = 1` through the injected api-client seam, the recovered artifact byte-matches the cached copy (both are the delivery pipeline's withheld artifact: for a held foreign sender, the untrusted-envelope-wrapped text), a cached body never triggers a read, and a released record is never recoverable; store held state the cursor/allowlist machinery's way — `held.json` (0600, atomic writes, inside the 0700 realm directory, safe-key realm check, bounded read via a constant derived in `constants.mjs`), missing/corrupt degrading to the empty default, a read never creating state; serialize read-modify-write cycles per realm through a promise chain (the cursor chain's discipline) and keep reads off it (atomic renames hand them a whole old-or-new file); register held rows AFTER the cursor persists, driven ONLY by matrix-held rows, with failures reported as additive notes on the read result — the consumed page is returned either way; surface refusals from the async-facing mutators as REJECTED promises, never synchronous throws past the adapter's error handling; keep the message_read page shape untouched (held rows stay exactly 3.2's additive `held`/`held_reason` extension) and grow the tool surface additively by exactly two closed-schema tools after the trust pair; build the tests in the house style — real spawned server children, real MCP stdio children, the real api-client for recovery, real keypairs, zero wire mocks, oracles as literals, and the composed-layer honesty statement (a v0.2 connection cannot produce a hold; the REAL matrix driven with transport 'remote' over REAL server reads stands in, as in 3.2) in the test file header and the evidence note.

**Block If:** any body byte of a held message reaches any tool result — cached, evicted, or recovered — halt; that is the story's Plugin-enforced core. Eviction deletes a record, flips an approval, or skips a message — halt; it may only drop a cached body copy. Recovery depends on the cache (no point-read path), reads with the wrong shape, or serves a released record — halt. The cursor stalls on, or loses, held state — halt (FR-20). The held list or count exposes a field outside the metadata whitelist — halt. A tool can reach `heldBody` or `heldClear`, or any release/auto-approve path exists — halt; release is the human CLI's decision (Story 3.4). The state file drifts from the state-file discipline (permissive modes, non-atomic writes, unbounded reads, unsafe realm keys) — halt. Registration blocks or fails a read whose cursor already advanced — halt.

**Never:** do not expose a held body, a body accessor, or a release verb through any tool, schema, or argument name; do not let `heldList`/`heldCount` return more or fewer fields than the enumerated metadata set; do not delete a held record on eviction or bound the LISTING by the cache cap; do not point-read with any shape other than `after_seq = seq − 1, limit = 1`, and do not cache the recovery result over the drop-oldest discipline (recovery serves the human preview; it does not refresh the cache); do not restate a numeric limit outside `server/constants.mjs` — the file's read bound is the derived `HELD_STATE_MAX_BYTES`, and the cache cap is the existing `HELD_CACHE_MAX`; do not change the frozen message_read row shape beyond 3.2's additive fields, the cursor discipline, or any wire route (the held tools never cross the wire — AD-8 untouched); do not register delivered rows, rows without a string body artifact, or rows into a different room than the read; do not build Story 3.4's CLI here; do not skip, `.only`, or todo any test, and do not compute expected values from production modules — the metadata key sets, eviction outcomes, and recovery shapes are literal oracles in the test file.

## Design Notes

**Why the whitelist projection is the whole metadata-only guarantee.** A blacklist ("strip the body field") fails the moment someone adds a field; a whitelist that BUILDS the agent-visible row cannot regress. The AC's enumeration (realm, sender Chat ID, fingerprint, room, seq, time, size, held count) is therefore encoded twice — once as the projection's fixed key list, once as a literal oracle the test asserts on every row of every listing — and the body copy's absence is checked against hostile content including an actual envelope-wrapped artifact with a terminator attack inside, over the real tool result JSON.

**Why eviction is drop-oldest-by-cached_at over an append-ordered file.** Registration appends records (the listing's natural history), but the body cache's fairness rule is recency of CACHING, not of registration: a re-delivered held message refreshes its copy in place (keeping the record's original registered_at), so its copy becomes the newest regardless of file position. Eviction therefore scans the body-carrying entries for the oldest `cached_at` — ISO timestamps compare lexicographically — and drops exactly one copy per overflowing registration, with list position breaking same-millisecond ties so the discipline is deterministic even under burst registrations.

**Why recovery returns the envelope-wrapped artifact instead of the raw log text.** The pipeline's job is to show the human exactly what was withheld — nothing more, nothing less — and what was withheld is the artifact the delivery pipeline produced: the untrusted-envelope-wrapped foreign body. Because the point read goes through the same api-client path, cached and recovered forms are byte-identical by construction (the test byte-matches them against the original page), the `size` metadata describes the same artifact, and the preview never silently downgrades the framing the plugin enforces everywhere else. Story 3.4's CLI can present the framed preview as-is — honest about both the content and its provenance.

**Why the cursor persists before registration (and why registration failure is only a note).** FR-20's invariant is directional: a held message must never stall the cursor, and advancing the cursor must never lose held state. Persisting the cursor first makes the first half true by ordering (the held work cannot block it); making registration failure note-only makes a held-pipeline fault incapable of discarding a consumed page; and the separate-file, separate-key design ((realm, room, seq) in held.json vs (realm, room) in cursors.json, never read by each other's machinery) makes the second half true structurally — proven both ways at the file layer and end-to-end over the real tool surface (consume → no re-delivery → cursor unchanged → held list intact).

**Why the mutators reject instead of throw.** `registerHeldMessages` and `heldClear` run inside the adapter's read path and (in 3.4) the CLI; a synchronous throw from a non-async function would skip the caller's await-shaped error handling — in the adapter's case, escaping past the code that reports `cursor_persisted`/notes on the returned page. Validating inside the queued operation keeps every refusal a rejected promise (chained per realm, so a failed write also never poisons the chain), which the test pins with `assert.rejects` on every malformed input.
