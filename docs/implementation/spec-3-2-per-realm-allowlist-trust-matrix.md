## Intent

**Problem:** `docs/epics.md:383-391` (Story 3.2) requires trust bound to fingerprints per realm, so that names never inherit trust. FR-10 (`docs/prds/prd-agent-room-2026-09-20/prd.md:195-200`) fixes the default matrix — own-Actor delivers (verifiable by comparing the local key fingerprint, including the same-Actor Direct Room), Local Mode same-OS-user senders deliver automatically, Remote allowlisted Actors deliver automatically, and any other Remote sender — including one claiming to be on the same machine — is held — with accept-all as a per-realm human opt-in, re-used Chat IDs never inheriting trust, a replaced key starting untrusted, and a remove action that affects future ingestion only. The substrate has the receiving side's plumbing but none of the decision: `applyUntrustedEnvelope` (`server/client/api-client.mjs`) wraps every foreign body but delivers all of them; the MCP adapter's `message_read` (`server/mcp-stdio.mjs`) projects the wrapped page verbatim; the only per-realm plugin state is the cursor file. There is no allowlist, no matrix, no held representation, and no way for a human's trust decision (Story 3.4's CLI) to exist at all — FR-10 is prose without a state machine.

**Approach:** one plugin-layer slice — the trust decision is CLIENT-side by design, because the server already enforces DM privacy (third-Actor denial) and this story is about what the RECEIVING agent's tool results show. (1) `server/client/trust.mjs` (new) owns the matrix and the storage: `evaluateSender({senderFingerprint, ownFingerprint, transport, allowlist})` → `{decision, lane, reason}` is the pure matrix in FR-10's priority order (own fingerprint → deliver/enforced; local transport — the receiving installation's own session authenticated through the local token file path — → deliver/instructed, honestly labeled because the OS-user boundary is a human convention; allowlisted fingerprint → deliver/enforced; accept-all → deliver/instructed; anything else → hold/enforced, fail-closed on missing fingerprints and unknown transports), plus `applyTrustMatrix(page, …)` as the delivery-time application (delivered rows pass untouched; held rows keep every metadata field, have their text replaced by a literal marker carrying sender metadata and the recorded reason — no body byte — and gain additive `held`/`held_reason` fields), plus the allowlist file machinery at `PLUGIN_DATA/realms/<realm_id>/allowlist.json` (0600, atomic writes, the cursor machinery's discipline: missing/corrupt degrades to the default `accept_all: false, entries: []`, malformed entries are dropped not trusted, unsafe realm keys are coded refusals) with `setAllowlistEntry` (idempotent add preserving the original `added_at`, explicit idempotent remove) and `setAcceptAll` — the latter exported for the human CLI (Story 3.4) and deliberately reachable from NO agent tool. (2) The api-client records its own connection mode: the transport getter returns 'local' once the live session authenticated through the local token exchange (null before; Epic 4's challenge path will mark 'remote') — the plugin knows the transport from its own connection mode, never from a claim. (3) The MCP adapter wires both in: `message_read` evaluates every row of every page through the matrix against the realm's stored allowlist before the tool result exists (held rows' envelope-wrapped bodies never surface; the cursor still advances — ingestion and trust are independent per FR-20), and two additive tools join the surface — `room_trust_list` (realm, accept_all, entries) and `room_trust_set {target_fingerprint, allowed}` (idempotent add/remove; `target_fingerprint` reuses the existing vocabulary name for a fingerprint that is an operation's TARGET, never sender identity, exactly like `room_direct_open`'s disambiguator) — both operating on plugin-local state only and making no wire-API change. (4) The proof: `tests/trust.test.mjs` (new) covers every AC row — the full matrix grid, the D13 rows (a reused Chat ID or replaced key inherits nothing; a remote sender whose Chat ID claims same-machine is held because names are not an input), removal re-holding over a REAL file while already-ingested text stays delivered, storage permissions/defaults/refusals, and the real tool surface and message_read path over real spawned server and MCP children — plus the filled 3.2 entry in the AC evidence file, a dated additive spine amendment (AD-12), and this spec.

## Boundaries & Constraints

**Always:** keep the decision client-side in the plugin layer — the server never learns an allowlist exists (AD-12: trust decisions never leak into the server's client-request path); key the matrix on fingerprints only — the sender's Chat ID is deliberately absent from `evaluateSender`'s signature, so no name claim can move a decision (D13); label the lanes honestly per NFR-4 — the local-transport and accept-all deliver lanes are 'instructed' (the OS-user boundary and blanket human approval are conventions; same-user processes are not cryptographically distinguishable), the own-Actor/allowlisted comparisons and the hold are 'enforced' (D17: wrapping/omitting text is the Plugin-enforced lane); fail closed — a row with no fingerprint is foreign, a transport that is not exactly the local token path evaluates as remote, a corrupt allowlist file degrades to accept-all false with no entries, and a hand-mangled file drops malformed entries instead of trusting them; store state the cursor machinery's way — `allowlist.json` (0600, atomic, inside the 0700 realm directory, safe-key realm check, bounded read via the shared `readJsonFile`), keyed by realm id and by nothing else; make removal a future-only action — evaluation happens at delivery time, so already-ingested text is never retroactively withdrawn and the durable log is never rewritten; keep the held representation minimal and honest — the marker text is plugin-authored (it frames no foreign body, so no untrusted envelope rides it), carries the sender chat id and fingerprint and the recorded reason, and never carries a body byte (the full held pipeline is Story 3.3's and none of its machinery — cache, counts, recovery, release — is built here); keep the envelope untouched — delivered foreign rows arrive exactly as `applyUntrustedEnvelope` wrapped them, and the frozen 1.7 row shape is extended only additively on HELD rows (`held`, `held_reason`); make accept-all structurally unreachable from the agent surface — the tools' schemas close without it, `TOOL_ARGUMENT_FIELDS` rejects it as an unknown field, and only the exported storage function (Story 3.4's CLI) can flip it, defaulting to false everywhere; grow the MCP surface additively by exactly two tools appended after the frozen five, with `target_fingerprint` as the argument name (the established vocabulary for a target fingerprint, keeping the NFR-3 identity-smuggling denylist intact) and every schema closed with `additionalProperties: false`; advance the cursor on held pages exactly as before (FR-20: held state is separate from ingestion); build the tests in the house style — real spawned server children, real MCP stdio children, real keypairs, zero wire mocks, oracles as literals in the test file, deadline-bounded waits, ordered `t.after` cleanup — and prove the remote lane at the matrix and application layers composed with the REAL allowlist files the real tool surface wrote, stating plainly in the test file header and the evidence note that a v0.2 connection cannot produce an end-to-end hold by construction; make the spine amendment strictly additive and dated (AD-12, where the plugin-local trust state decision lives), recording why AD-8 needs no change (the trust tools never cross the wire); fill the 3.2 evidence entry with the real test titles and a note stating what the evidence does NOT prove.

**Block If:** any matrix cell delivers a sender the matrix must hold, or holds a sender FR-10 delivers — e.g. a reused Chat ID inheriting trust, a replaced key riding an old entry, a local-claiming name delivering on a remote transport, or accept-all defaulting to true from a missing/corrupt file — halt; that is a defect in the matrix or its defaults, not a test correction. Any body byte of a held message reaches a tool result — halt; the withholding is the story's Plugin-enforced core. The allowlist file drifts from the cursor discipline (permissive modes, non-atomic writes, a realm id used as a path without the safe-key check) — halt. An agent-invocable path to accept-all appears (a tool argument, a tool result side effect) — halt; it is a human CLI decision by FR-10 and the AC. The five frozen tools' contracts change (names, schemas, argument allowlists, response shapes) rather than appending two new tools — halt; the growth must be additive. The trust evaluation moves server-side or the allowlist crosses the wire — halt; AD-12 forbids both. A removed entry retroactively withdraws already-ingested text or rewrites the durable log — halt; removal affects future delivery only.

**Never:** do not put the sender's Chat ID (or any name) into the matrix's inputs, the allowlist entries, or the stored file — trust binds fingerprints (D13), and the test asserts the stored JSON contains no name; do not label the local-transport or accept-all lanes 'enforced' or describe the OS-user boundary as cryptographically meaningful anywhere in production wording (NFR-4); do not build Story 3.3's pipeline (held cache, held counts, point-read recovery, release) or Story 3.4's CLI here — the held representation is minimal by design and the evidence note says what is deferred; do not add a wire route, wire field, or operator route for trust (AD-8 untouched; AD-13: no operator routes); do not expose `setAcceptAll` through any tool, and do not let any tool result or argument name suggest otherwise; do not restate a numeric limit literal outside `server/constants.mjs` (AD-9's scan) — the storage reuses the shared `readJsonFile`/`atomicWriteJson` bounds; do not change the untrusted envelope's template, version, or warning text, and do not wrap held rows in it (they carry no foreign body); do not let a held row's `text` contain any substring of the original body — the test proves it against hostile content including an envelope-wrapped body; do not modify the frozen read/send/idempotency/cursor contracts beyond composing the matrix into the `message_read` result projection; do not touch the retired v0.1 modules; do not skip, `.only`, or todo any test, and do not compute expected values from production modules — the held marker and matrix verdicts are literal oracles in the test file.

## Design Notes

**Why the matrix is a pure function with the Chat ID missing from its signature.** The AC's dangerous rows are all name-shaped: a reused Chat ID, a replaced key, a sender "claiming same-machine". The strongest way to make names never inherit trust is to make names structurally inert — `evaluateSender` has no name parameter, so no claim can be an input, and the D13 test proves the property at the application layer by splitting two rows that share one Chat ID purely on fingerprints. The lane labels then do the honesty work NFR-4 demands: the two deliver paths that rest on human conventions (the OS-user boundary, blanket approval) are labeled Instructed in the returned verdict itself, so no consumer can mistake them for verified sender properties.

**Why the local lane delivers everything on a Local Mode connection — and why that is honest.** FR-10's matrix is deployment-aware: a Local Mode realm's enrollment boundary is the 0600 local token file, so every sender on that loopback server crossed the same OS-user boundary the README already describes honestly ("it does not isolate mutually hostile processes running as the same user"). Auto-delivering there is D15(6)'s ratified default ("Local Mode auto-delivers"), and the verdict says so with lane 'instructed' — the same honesty the PRD applies to approval provenance. The remote lane is where enforced trust lives: without the OS-user boundary, only exact fingerprint equality (own Actor, allowlisted entry) delivers, and everything else is held — including a sender whose Chat ID claims locality, because the claim is a name and names are not an input.

**Why accept-all is delivered with the Instructed lane and reachable from no tool.** Accept-all is the one branch that delivers WITHOUT any per-sender verification — closer in kind to the local boundary than to the allowlist's exact fingerprint comparison. Labeling it Instructed keeps the verdict honest ("a human opted this realm in") and keeps FR-10's "untrusted framing always remains" the operative safety net (the envelope on delivered bodies is unchanged everywhere). Structurally, the flag lives in the same file as the entries but flips only through `setAcceptAll`, which no tool calls: the schemas close without an `accept_all` field, the argument allowlist rejects it as unknown before any call, and the test smuggles it to prove the refusal changes nothing. Story 3.4's CLI is the only intended writer.

**Why removal re-holds without any history machinery.** The matrix evaluates at delivery time and holds nothing back — there is no queue to withdraw from, so "already-ingested text is not retroactively withdrawn" is true by construction rather than by compensation. The test pins the two halves: the in-hand page object from the earlier delivery keeps its body (the matrix never mutates delivered rows), and the durable log — read directly over HTTP from the real server — still returns every body. Removal's only effect is on future evaluations, which the re-composed matrix demonstrates by holding the same row that previously delivered.

**Why the held representation is a marker string plus two additive fields.** Story 3.3 owns the full metadata-only pipeline; Story 3.2 needs the hold to be real (no body reaches the tool result) and informative (the agent sees WHY, and the human-facing metadata survives). Replacing the row's `text` with a deterministic marker keeps the frozen page shape (the row still has its eight frozen keys; held rows add `held`/`held_reason` additively), lets the provenance fields ride in their frozen slots AND in the marker (self-describing when read in isolation), and makes the test's job mechanical: a literal marker oracle, a byte-for-byte comparison, and a body-substring absence check against hostile content — including an envelope-wrapped body, proving the wrapping itself never leaks through a hold.
