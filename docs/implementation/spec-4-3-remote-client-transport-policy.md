## Intent

**Problem:** `docs/epics.md:461-467` (Story 4.3) requires the client half of Remote Mode. The substrate is complete and waiting: the challenge lane is live and proven over the loopback (`POST /api/auth/challenge` / `answer`, Story 4.1 — a declared-remote installation already authenticates through it and never touches the local token file), invite enrollment is live (Story 4.2 — an enrolled key's fingerprint row is the answer gate's input), and AD-10's Remote Mode definition names the deltas — "configured URL, TLS required, challenge auth, invite-gated enrollment" — of which only the challenge-auth quarter exists. What does not exist: any way for a client to point at a REMOTE server. `createAgentRoomClient` hard-wires `host: '127.0.0.1'` + an `ensureServer`-resolved port (the FR-1 Local Mode bootstrap), and the CLI host has no remote grammar — so the 4.1 review-patch guarantee ("a declared-remote installation never touches the local token") has no real remote path to hold on, and the 4.2 residual risk ("the enroll route has no transport story; configured server URLs, HTTPS verification, and remote bootstrap are Story 4.3's") stands.

**Approach:** one small client-side configuration module plus the remote branch of the existing challenge path — no wire change, no route change, no server change. (1) `server/client/remote-config.mjs` owns the persisted configuration and THE TRANSPORT POLICY: a configured server URL must parse as an https:// URL with a hostname (plaintext `http://` is REFUSED with a coded error naming the refused scheme, before any wire work; non-origin URLs — paths, queries, fragments, credentials — are refused with their reasons), stored at `PLUGIN_DATA/remote-config.json` (0600, atomic, exactly one origin — ONE SERVER ACTIVE AT A TIME; setting again replaces and the per-realm state of the replaced server stays on disk under its realm id, inert, because a different server is a different realm with fresh trust per AD-14/D13). Reads re-validate: a hand-edited plaintext URL refuses exactly like a freshly typed one, and a corrupt file refuses rather than silently falling back to Local Mode (the safe direction is refusing, never retargeting). (2) The api-client gains the remote branch: an explicit `serverUrl` factory option (the direct declaration; tests/embedding hosts) or a persisted config makes the client skip `ensureServer` ENTIRELY — no local bootstrap, no runtime record, no local token file, the 4.1 review patch's real path at last — and join every API path onto the configured origin over `node:https` with Node's DEFAULT certificate and hostname verification (no override exists anywhere in the client tree; a TLS refusal is a transport error whose code is never ECONNREFUSED, so it surfaces immediately instead of entering the reconnect schedule). The credential lane is the 4.1 challenge lane (a configured origin pins the fail-closed pre-auth `remote` transport mark exactly as the env declaration does); the reconnect recovery probe aims at the CONFIGURED origin's `/health` instead of the local runtime record; a `not_enrolled` answer surfaces as the same coded error with actionable enrollment guidance (the operator's invite flow — the client never auto-enrolls); and an ENROLLED key's reconnect IS the challenge lane — no invite, no re-enrollment (AC-2; enrollment does not expire in v0.2). The default without configuration is byte-for-byte unchanged: Local Mode via ensureServer (FR-1). (3) The shared CLI host gains the `remote` command family — `remote set <https-url>` / `remote show` / `remote clear` — the invite family's JSON-lines grammar and exit codes (0 ok, 1 refusal, 2 usage), extending the one dispatch later operator-style families reuse (review MED-1's host rule).

## Boundaries & Constraints

**Always:** keep the transport policy in ONE place — `validateRemoteServerUrl` is the only scheme check, and both the CLI family, the config module's read path, and the client factory route through it, so a plaintext URL is refused identically at set time, at load time, and at client-construction time; keep the persisted file to exactly ONE origin (save replaces wholesale) and project the replacement honestly (`previous_server_url` on the CLI receipt); make every read re-validate and every corrupt file an actionable coded `invalid_request` — never a silent fallback to Local Mode; keep the remote branch credential-clean — no `ensureServer`, no runtime-record read, no local-token read or creation, the challenge lane the only credential path, the `remote` transport mark pinned pre-auth (fail-closed) and earned post-exchange; keep Node's DEFAULT TLS verification untouched — no certificate check, hostname check, or env opt-out anywhere in the client tree (a structural pin enforces this); surface `not_enrolled` as a coded, actionable refusal that names the operator's invite flow and states that the client never enrolls itself; aim the reconnect recovery probe at the configured origin's `/health` with the same bounded read-only shape as the local probe; keep the FR-1 default byte-identical — with no config and no option, the local bootstrap path is untouched code on untouched flags; keep the config file 0600, atomically written, bounded on read, inside PLUGIN_DATA (client state — never the shared data dir, AD-12); extend the existing CLI dispatch and its single JSON-error printer, never a new entrypoint; test over real processes — the journey row is a real child over real TLS with real server code, the refusal rows are real TLS servers, and the counted negatives (no invite token, no enroll request, no local-token request on any hop) span BOTH wire legs.

**Block If:** a plaintext (http://) remote URL is ever stored, loaded, or dialed — halt; the AC's letter is HTTPS with normal verification, plaintext remote REFUSED. Any certificate-verification bypass appears (`rejectUnauthorized`, `NODE_TLS_REJECT_UNAUTHORIZED` honored by our code, a replaced `checkServerIdentity`) — halt; the transport policy IS default verification. Two servers are ever active for one installation — halt; one origin per config file, replacement not addition. A remote client reads the local token file, the runtime record, or boots a loopback server — halt; the declared/configured discipline means the OS-user boundary is not its own. A corrupt remote config silently degrades to Local Mode — halt; the safe direction is a coded refusal. The client auto-enrolls on not_enrolled — halt; enrollment is the operator's invite flow (Story 4.2, AR-13), and the coded error must say so. A second CLI entrypoint appears for the remote family — halt; the shared host extends.

**Never:** do not change any route, request field, response field, status, or constant (the wire is frozen; this story is client-side configuration plus the already-frozen challenge path); do not add retry/CA/TLS options to the client factory (a CA option is a verification-base option — the policy is Node's default stack, full stop); do not implement ban, capacity, or any other operator command (4.5/4.6 own those, on this host); do not touch the trust matrix's cells, the MCP tool schemas, the viewer, or the enrollment/challenge routes' behavior; do not persist the remote URL per-realm or under `realms/` (the URL is pre-realm identity — it decides WHICH realm, it is not state OF one); do not restate a bound or a fingerprint definition; do not skip, `.only`, or todo anything; do not commit; do not claim literal cross-machine deployment as proven (the harness reaches the wire through a loopback TLS front — the honest scope is recorded in the test file header and the evidence note; the dress rehearsal is Story 4.8's).

## Spec Change Log

- 2026-09-29 (this story): spec created from `docs/epics.md:461-467`. Four planning decisions made where the epic text is silent, all grounded and recorded here rather than invented silently. (1) **The URL is the ORIGIN**: the config stores a normalized origin (scheme + lowercase host + explicit port only — no path, query, fragment, or credentials), because the client joins API paths onto the base and a path-bearing URL would silently change every request's shape; v0.2's deployment recipes front the root, and a subpath deployment needs a different joining contract to be honest — refused with its reason until then. (2) **Corrupt config refuses, never falls back**: a broken remote configuration degrading to Local Mode would silently retarget the installation's traffic to a different server — the safe direction is a coded, actionable refusal (fix, re-set, or `remote clear`), mirroring `loadChatIdConfig`'s discipline rather than the allowlist's degrade-to-default (which guards a trust WIDENING input in the opposite direction). (3) **The replaced server's realm state stays on disk, inert**: per AD-14 the realm id comes from the server, so a different server is a different realm and per-realm trust state under `realms/<old_realm_id>/` cannot influence the new one — deleting it would destroy history (a switch BACK to the old server revives it); the replacement test pins byte-identity of the old realm state across a re-set. (4) **The journey's honest TLS scope**: the happy path needs a certificate Node's DEFAULT verification trusts and `tls.rootCertificates` is frozen by design, so the journey runs in a spawned child with `NODE_EXTRA_CA_CERTS` pointing at a test CA — Node's own documented private-root mechanism, which ADDS a root without touching verification strictness — while the in-process self-signed row proves a certificate OUTSIDE the store is refused by the same code with zero answered requests. The front is a loopback TLS terminator proxying to the loopback plaintext backend — AD-11's permitted shape and the self-hosting guide's recipe.

## Design Notes

- **Why the policy lives in one validator that everyone calls.** The AC's negative ("plaintext remote is refused") is only as strong as its weakest caller. Three surfaces could otherwise drift: the CLI at set time, the module at load time (a hand-edited file), the factory at construction (an option or a loaded value). One `validateRemoteServerUrl`, called by all three, makes the refusal byte-identical everywhere and gives the structural story one home — and the read-time re-validation is what makes hand-edited files non-privileged.
- **Why `saveRemoteConfig` replaces rather than merges, and why nothing is deleted.** "One server is active at a time" is a file invariant: the file IS the active server declaration. Replacement is a whole-file atomic write, so there is no intermediate two-server state to reason about. The OLD server's realm directories are deliberately untouched: they are keyed by realm id (AD-14), a different server mints a different realm id, so the old state is unreachable-by-construction — deleting it would buy nothing and destroy the installation's history if it ever points back.
- **Why the client pins `remote` pre-auth on a configured origin.** The trust matrix's transport input fail-closes toward hold; the env declaration (3.5) pins `remote` pre-auth so an unauthenticated configured client can never read as local. A configured origin is the same declaration in persisted form — talking to a server across the network IS the remote lane — so it pins identically, and the mark is still EARNED only after the challenge exchange.
- **Why a TLS refusal must not enter the reconnect schedule.** The FR-12 schedule exists for ECONNREFUSED (outcome unknown — the recorded server is gone and may come back). A certificate-refusal code is never ECONNREFUSED: the outcome is KNOWN (the connection was refused by policy), the server will not become more trustworthy by waiting, and a 1s→60s loop on a policy refusal would be a hang wearing a costume. The refusal surfaces immediately.
- **Why the recovery probe re-aims instead of being skipped.** The remote reconnect loop reuses FR-12's machinery unchanged; only its probe target differs. The local probe reads the runtime record of a data dir a remote installation has no business reading; the remote probe does the same bounded, read-only `/health` check against the configured origin. Recovery detection stays "read-only, exactly the two inputs the staleness rules trust" — the URL and the probe.
- **Why `not_enrolled` gets an enhanced message but the same code.** Story 4.1's tests (and any caller) key on the code; the actionable guidance is the 4.3 addition. The message names the fingerprint, the server host, the operator's `invite mint` flow, and the once-only nature of enrollment — the human can act without reading documentation — and states the negative explicitly (the client never enrolls itself) because that refusal is a policy promise, not an implementation gap.
- **Why the CLI family reuses the invite grammar verbatim.** HCI-3's grammar (JSON lines, 0/1/2) is the established machine contract of the CLI host; a second output style for a sibling family would fork the contract the host exists to keep single (review MED-1). The remote family is the installation's surface rather than the server host's, but the OUTPUT contract is the host's, not the boundary's.
- **Why the driver injects fresh registries per restarted server.** `startServer` instances in one process share the process-default session/live registries; without injected fresh registries the "restart" legs silently inherit the predecessor's sessions — the harness would prove less than it claims (the first run's empty presence and missing re-auth exposed exactly this). Real restarts share nothing; the harness now models that.
