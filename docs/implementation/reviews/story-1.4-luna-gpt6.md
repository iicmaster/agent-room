## Verdict
FIX-FIRST — local auth assigns every installation the same Actor fingerprint, contradicting the frozen identity model and blocking correct 1.5–1.8 participant behavior.

Evidence boundary: source and test files were inspected and hashes rechecked. Tests were not executed in this read-only audit. The spec records 157/157 for a prior run at lines 114, but that result was not independently reproduced here.

## Findings
- [blocker] F1 — Local sessions bind to the shared token, not the installation key. server/api/session.mjs:30-37 hashes the local token; server/api/server.mjs:124-130 passes that digest to issue(); server/api/routes.mjs:45 accepts no public_key on /api/auth/local. This makes all local installations one Actor even though docs/implementation/epic-1-context.md:25-26 and ARCHITECTURE-SPINE.md:71-73 require one keypair and a fingerprint over its raw 32-byte public key. D13 addendum.md:19 keeps Actor identity key-bound while distinguishing Sessions by Chat ID. Fix before Story 1.5: accept the already-frozen public_key field on local auth, validate its 32 raw bytes, and bind the session to sha256(raw public key); retain the local token only as the OS-user bootstrap credential. Amend the Story 1.4 contract and route tests; do not describe public-key presentation as proof of possession.
- [warning] F2 — The no-state-on-rejection contract conflicts with first-use token creation, and existing file mode is not enforced. server/api/server.mjs:118-128 creates the token file before comparing a presented Bearer, so the first wrong credential returns 401 after writing state; tests/local-auth.test.mjs:305-318 asserts this. This conflicts with the blanket rule in the spec at line 27, while its matrix at line 47 permits the behavior. The zero-state test at tests/local-auth.test.mjs:274-293 hashes only database files. Also, server/api/local-token.mjs:31-40 and server/runtime.mjs:131-135 validate file type, symlink status, and size but accept an existing token file with mode other than 0600. Create the token before handling requests or explicitly narrow the rejection invariant, and enforce 0600 on every accepted token file.
- [warning] F3 — Readiness failure can leave the detached server alive. server/client/ensure-server.mjs:351-385 unreferences the child, throws on readiness timeout at line 383, then only releases the lock in finally; it never terminates or waits for the child. A slow child may later publish runtime.json and keep a listener after ensureServer reports failure. On every post-spawn failure, stop and reap the owned child before releasing the lock; cover a child that stays alive but never becomes ready.
- [warning] F4 — Stale-state rules need reconciliation and stronger record identity. The audit brief asks for dead-pid plus unreachable-health proof for both the lock and runtime.json; ensure-server.mjs:255-274 uses age plus dead owner for a lock. That matches the Story spec at lines 27 and 91 and AD-10 at ARCHITECTURE-SPINE.md:125, which require health proof for runtime.json only. Resolve this discrepancy explicitly rather than silently changing the recorded lock rule. Separately, ensure-server.mjs:159-179 unlinks the runtime path after an awaited probe without checking that the file still contains the record it inspected; a racing starter can publish a replacement record in that gap. The half-stale reuse at lines 124-134 accepts any Agent Room health response, while server/api/server.mjs:303-309 records only pid, port, and version, so it cannot prove the responder is the same realm. Re-read and compare the record before unlinking; bind a reuse probe to a stable realm identifier or refuse reuse when identity is unproven. Never signal a foreign process.
- [warning] F5 — The newly registered pre-auth route has no effective budget. AD-7 requires per-source pre-auth and global-floor budgets (ARCHITECTURE-SPINE.md:87), but server/api/pipeline.mjs:207-217 makes BudgetStage a pass-through while server/api/server.mjs:124-130 now issues a session for each valid local-token request. A non-OS-user can reach loopback health and send repeated rejected auth requests but cannot read the 0700/0600 credential; a compromised same-OS-user client can read the shared token and mint sessions. Repeated successful issuance grows the in-memory Map (server/api/session.mjs:49-62). Implement the pre-auth budget before treating this route as protected, or record this exposure and bound issuance as an explicit gate.

## Open-question opinion
- John (PM): Public-key binding is a gate before Story 1.5; the Actor identity feeds session, presence, trust, and Direct Room behavior.
- Sally (UX): A token digest could only be a temporary bootstrap principal if Story 1.5 must rebind it before any actor route is usable. Story 1.4 already issues a bearer accepted by the actor verifier, and no such transition exists, so the current design is not shippable.
- Vex (security): The local Bearer proves access to the OS-user boundary; public_key names the installation Actor but is not proof of possession. Bind the fingerprint without claiming a local signature check. A same-OS-user compromise remains inside the stated trust boundary.
- Recommendation: bind local sessions to SHA-256 of the caller's validated raw 32-byte public key; keep the shared token as the bootstrap credential. Two installations must produce distinct Actor fingerprints; multiple Sessions from one installation may share that Actor fingerprint while using distinct Chat IDs. The current no-identity-fields clause in the Story spec and route table must be amended explicitly.
