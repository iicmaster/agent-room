# Story 1.5 Audit — codex-advisor[luna] (gpt-6-luna[max])

## Verdict
FIX-FIRST — the documented durable heartbeat hook is memory-only, so Story 1.6 calling touch() alone leaves active claims stale and eligible for pruning.

## Findings
- [blocker] touch() does not refresh durable claim recency — server/core/session-registry.mjs:158-167 only changes the in-memory row; the spec says the hook refreshes the durable claim at docs/implementation/spec-1-5-chat-id-connect-rename-durable-claims.md:31,79. The only persistence callback is wired on connect/rename at server/api/server.mjs:198-215. An active session that only heartbeats can therefore retain an old database timestamp and lose its offline claim to the seven-day prune. Fix the handoff contract: either make the heartbeat path persist the updated claim in the same operation, or require Story 1.6 to upsert it explicitly and test that the stored last_seen_at advances.
- [warning] last_seen_at can move backwards — server/store/room-log.mjs:1081-1096 accepts lastSeenAt and unconditionally assigns excluded.last_seen_at; server/store/room-log.mjs:215-224 accepts any parseable timestamp. The current HTTP caller omits lastSeenAt (server/api/server.mjs:211-214), but another store caller can submit an older value, and wall-clock rollback can do the same through the default. This can reorder ambiguity candidates and make a claim prune early. Update recency monotonically while still refreshing chat_id_display.
- [warning] seven-day pruning does not hard-bound claim count — each new (normalized name, Actor) pair inserts a durable row (server/store/room-log.mjs:1089-1096), and historical pairs remain until age-pruned (server/store/room-log.mjs:1072-1080). The request-budget stage is still a pass-through (server/api/pipeline.mjs:207-217), so one valid session can create many unique names by repeated renames inside the retention window. The current host is loopback-only (server/api/server.mjs:357-374), which limits exposure today. Before remote access, apply the planned request budget or an explicit storage/cardinality bound; TTL alone bounds age, not rows.
- [warning] rejection tests omit sliding auth-session state — the spec says every rejection makes no state change (docs/implementation/spec-1-5-chat-id-connect-rename-durable-claims.md:27), but a valid actor-token verification extends expiresAt (server/api/session.mjs:97-104) before request-field validation and the handler (server/api/pipeline.mjs:196-203,372-384). The new rejection tests inspect claim rows, not token expiry (tests/session-routes.test.mjs:533-587). Preserve the prior sliding-TTL behavior, but clarify whether “zero state change” covers only chat-binding/store state and test that boundary.
