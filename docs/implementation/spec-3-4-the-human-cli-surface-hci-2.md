## Intent

**Problem:** `docs/epics.md:407-418` (Story 3.4) requires terminal commands to inspect and release held messages, so that trust decisions are the human's — informed and honest. HCI-2 (`docs/epics.md:108`) fixes the flow: `agent-room held list`, full preview on `agent-room held show <id>` (the ONLY surface where held body text appears, never an MCP tool result), release (`agent-room allow <chat-id>` reporting realm + fingerprint), and remove (future ingestion only), with approval stated as a human convention (Instructed) — same-user processes are not cryptographically distinguishable. FR-10 (`docs/prds/prd-agent-room-2026-09-20/prd.md:199`) binds the release to a human-operated terminal action resolving the Chat ID to the underlying key on the current realm, and `:201` binds point-read recovery to `after_seq = seq − 1, limit = 1` when the cache copy was evicted. The substrate is complete but headless: `server/client/held.mjs` exports `heldList`/`heldCount`/`heldBody`/`heldClear` (the body and release paths reachable from no tool — `server/mcp-stdio.mjs:88-97` imports only the metadata trio), `server/client/trust.mjs` exports `setAllowlistEntry` and `setAcceptAll` (the accept-all flip is "settable ONLY through the human CLI surface (Story 3.4)" — `server/client/trust.mjs:266-270`), and the `agent-room` bin (`server/cli/agent-room.mjs`) dispatches only `setup`, rejecting every other argv (`:255-260`). There is no command a human can run to see what is held, no way to preview a body, no way to allow a sender, and no human surface for accept-all at all — FR-10's release is prose without a terminal.

**Approach:** one CLI slice over the finished pipeline — no pipeline, tool, or wire change. (1) `server/cli/http.mjs` (new) hosts the setup command's `httpJson`/`bearerHeaders` verbatim (extracted, single home; `runSetup` imports them), so the new commands share one bounded round-trip helper. (2) `server/cli/held-commands.mjs` (new) carries the command bodies: `runHeldList`/`runHeldShow`/`runAllow`/`runAllowAll` with runSetup's injectable-deps shape (`input`/`output`/`sharedDataDir`/`pluginDataDir`), the CLI session discipline (exchange the shared data dir's local token plus the installation public key for a session token and NEVER bind a Chat ID — no `POST /api/session` — so the commands can never collide with the live MCP session's claimed name and leave zero presence/claim footprint), realm resolution from `GET /api/status` through the same `REALM_KEY_PATTERN` guard as the MCP adapter's `realmIdOf`, and the point-read seam for `heldBody` that applies `applyUntrustedEnvelope` exactly as the api-client does, so a recovered body byte-matches the cached artifact. (3) `server/cli/agent-room.mjs` grows a dispatch table (`setup`, `held list`, `held show`, `allow`, `allow-all`, `help`) with help text that states the Instructed honesty plainly. `held list` prints metadata lines with a stable `<room_id>:<seq>` id per row; `held show <id>` prints the metadata block plus the full body; `allow <chat-id>` resolves the name to a fingerprint from the current realm's held records and presence (case-insensitive, `--fingerprint` disambiguates, ambiguity and unknown names exit non-zero with candidates or guidance), saves the allowlist entry, and releases that key's held records; `allow <chat-id> --remove` removes the entry and touches nothing else; `allow-all`/`allow-all --remove` are the accept-all surface (explicit TTY confirmation for the blanket grant, none for the fail-safe removal). (4) The proof: `tests/cli-surface.test.mjs` (new) in the house style — real spawned server children, real held and allowlist state files, injected stream fixtures, literal oracles — plus the 3.4 evidence entry, a dated additive AD-12 amendment, and this spec.

## Boundaries & Constraints

**Always:** keep held body text confined to `held show`'s stdout — `held list` prints metadata only (the AC names `held show` as the only surface where held body text appears, so the list, the allow output, and every error message carry metadata at most); key every release on the FINGERPRINT, never the name — `allow` matches held records by `actor_fingerprint ===` the resolved fingerprint (D13; a reused name inherits nothing, and a record with a null fingerprint is never matched by name); resolve chat ids ONLY from the current realm's own evidence — the plugin-local held records (the senders actually awaiting a decision) and `GET /api/presence?include_offline=true` (online + offline-recently rows, both carrying chat id + fingerprint + last-seen) — compared case-insensitively per DR-1, merged by fingerprint, and never guessed at: zero candidates refuses, several refuse with the candidate list (fingerprint + source/last-seen), one proceeds; make ambiguity resolution explicit — `--fingerprint` must be a well-formed fingerprint AND, when the name has candidates, one of them, so the CLI can never allow a key that has nothing to do with the name the human typed; honor the pipeline's own APIs — release goes through `heldClear` per (room, seq), the allowlist through `setAllowlistEntry`, accept-all through `setAcceptAll`, the preview through `heldBody` with the point-read seam exactly `after_seq = seq − 1, limit = 1` through the injected function, and the recovered page wrapped by `applyUntrustedEnvelope` with the installation fingerprint before the seam returns it (byte-identical to the cached artifact — spec-3-3's recorded decision); keep the CLI session UNBOUND — the local-token exchange issues a session token bound only to the Actor fingerprint (`server/api/server.mjs:200-225`), so no `POST /api/session` is ever sent: no `chat_id_taken` collision with the live MCP session, no presence touch (the post-auth touch no-ops for an unbound session — `server/api/server.mjs:826-829`), no durable claim row, and no Chat ID in any CLI output (the commands never learn one); resolve the realm the MCP adapter's way — `GET /api/status` through `ensureServer` + the local token, guarded by `REALM_KEY_PATTERN` before any `PLUGIN_DATA/realms/<realm_id>/` path is built; state the honesty exactly — the help text says approval is a human convention (Instructed) and that same-user processes are not cryptographically distinguishable, and the literal phrase "never agent-invocable" appears NOWHERE (the AC's negative); confirm the blanket grant explicitly — `allow-all` requires an interactive TTY y/N confirmation and refuses non-TTY stdin with guidance (the setup command's established discipline, `server/cli/agent-room.mjs:14-16`), while `allow-all --remove` and `allow --remove` (both fail-safe directions) run without confirmation; make every failure actionable and coded — exit non-zero, one `agent-room <command> failed: <code>: <message>` line on stderr naming the failing input (grammar errors quote `CHAT_ID_INVALID_MESSAGE`; unknown names say where the CLI looked; ambiguous names list the candidate fingerprints; unknown held ids name the id), never a bare "invalid"; keep the mutators' rejection discipline — the async command bodies await `heldClear` (rejected promises), so a refusal surfaces as the command's coded error, never a synchronous throw past the dispatch; keep the runtime gate and the launched-directly discipline on the bin (`server/cli/agent-room.mjs:279-294` unchanged in shape) and keep `runSetup`/`SETUP_REQUIRES_TTY_MESSAGE` exported for the existing tests; build the tests in the house style — real spawned server children, real `held.json`/`allowlist.json` state written by the real pipeline functions (the composed-layer hold production of `tests/held.test.mjs`), injected stream fixtures for the confirmations, literal oracles for output lines and key sets, zero wire mocks.

**Block If:** any held body byte reaches stdout of `held list`, `allow`, `allow-all`, the help text, or an error message — halt; `held show` is the only body surface the story ships. Any tool result, MCP schema, or adapter import changes — halt; the tool surface stays exactly the nine tools and the adapter still imports only `heldList`/`heldCount`/`registerHeldMessages` (the `tests/held.test.mjs` source scan must stay green untouched). The CLI sends `POST /api/session`, creates a durable claim, or appears in presence — halt; the unbound-session discipline is the story's collision-freedom guarantee. Release matches held records by Chat ID instead of fingerprint, or `--remove` deletes held records, rewrites the durable log, or withdraws already-ingested text — halt; D13 and FR-10's future-only rule. Ambiguity resolves silently (picks a candidate without the human's `--fingerprint`), or `--fingerprint` allows a key outside the name's candidates — halt; HCI-4's "never a silent guess". `heldBody` recovers with any shape other than `after_seq = seq − 1, limit = 1`, re-caches the recovery, or serves a released record — halt; spec-3-3's recovery contract. `allow-all` flips accept-all without explicit TTY confirmation, or a missing/corrupt allowlist file evaluates to trust — halt; the blanket grant is the one action with no per-sender verification. A new numeric limit or error message is restated outside `server/constants.mjs` — halt (AD-9); this story needs zero new constants. The state files drift from the state-file discipline (permissive modes, non-atomic writes, unsafe realm keys) — halt; the CLI writes only through `setAllowlistEntry`/`setAcceptAll`/`heldClear`, which own the discipline.

**Never:** do not put held body text, a body accessor, or a release verb into any MCP tool, schema, or the adapter's imports (the nine-tool pin and the source scan are regression-guarded by existing tests); do not bind a Chat ID from any CLI command or print the configured one (the CLI has no session name — `config.json` is not read by these commands); do not resolve a fingerprint from anything the sender could have written — no message body, held marker text, or claim in a message is consulted, only the plugin's own held records and the server's presence rows; do not let `allow` clear other keys' held records, create an allowlist entry for an unresolved name, or report success without persisting the entry first; do not make `held show` print anything but the record's metadata and the exact artifact the pipeline withheld (no re-wrapping, no unwrapping, no truncation); do not add a `--json` mode, an operator route, a wire route, a new MCP tool, or a new constant; do not touch the frozen tool descriptors, the wire API, the pipeline modules' contracts (`held.mjs`/`trust.mjs` signatures stay as 3.2/3.3 shipped them), the setup command's behavior (its HTTP helper moves to `server/cli/http.mjs` verbatim — `tests/setup-command.test.mjs` stays green), or the retired v0.1 modules; do not skip, `.only`, or todo any test, and do not compute expected output strings from production modules — the help statement, error lines, and metadata line shapes are literal oracles in the test file.

## Spec Change Log

### 2026-09-29 — initial ready-for-dev plan
- Pinned Story 3.4 to baseline `42c89c945dfa8792908720573c6eeb08ebe9c0ad`; planning-time suite baseline at that revision: `node --test --test-timeout=300000` → 376 tests / 376 pass / 0 fail / 0 skipped (run before any change), and `node scripts/ac-sweep.mjs --epic 3` → verdict `gaps` with 3.4 and 3.5 unreported (the expected pre-story state).
- **Recorded decision — the CLI session is UNBOUND.** Every held/allow command exchanges the shared data dir's local token plus the installation public key for a session token and never sends `POST /api/session`. This is the load-bearing choice: the human runs these commands precisely while the MCP session is live, and Story 1.5 refuses a second live claim of the same name (`chat_id_taken`), so a binding CLI could never run against an active session. The exchange alone issues a token bound to the Actor fingerprint (`server/api/server.mjs:200-225` — no chat id is involved), the post-auth presence touch no-ops for an unbound session (`server/api/server.mjs:826-829`), and no durable claim row is written — zero footprint, zero collision. The commands therefore never read `config.json` and never print a Chat ID of their own.
- **Recorded decision — the `held show` id is `<room_id>:<seq>`, parsed at the LAST colon.** The held record's key is (room, seq) — the only stable identity the pipeline offers — and `held list` prints that id per row so the human copies it verbatim into `held show`. Room ids legitimately contain colons (`direct:sha256:…:sha256:…`), but the seq is always a colon-free positive integer, so splitting at the final colon is unambiguous; anything else is a coded malformed-id refusal naming the expected form. An index-into-the-listing id was rejected: it shifts on every release.
- **Recorded decision — `allow` resolves the name from exactly two local-truth sources: this realm's held records and `GET /api/presence?include_offline=true`.** The held records are the durable plugin-local record of the senders actually awaiting a decision (each carrying chat id + fingerprint); presence contributes online and offline-recently rows (chat id + fingerprint + last-seen, `server/core/session-registry.mjs:341-393`). Matching is case-insensitive per DR-1 and merged by fingerprint. `POST /api/rooms/direct`'s claims resolution was deliberately NOT reused: it OPENS a room (a state change, and one whose outcome the trust matrix then colors), which is wrong for a trust decision. The honest limitation: claims older than 24 h sit in the durable claims index beyond presence's window — but a sender old enough to have aged out of presence AND absent from the held records is not a release candidate this CLI can vouch for, so the name refuses with guidance instead of guessing.
- **Recorded decision — `allow-all` exists, with explicit TTY confirmation.** FR-10 grants a per-realm accept-all to "a human", 3.2 stored the flag with `setAcceptAll` reachable from no tool (`server/client/trust.mjs:266-270`), and spec-3-2's continuity note assigns the flip to 3.4's CLI — without it the flag is dead code and FR-10's sentence has no surface. The blanket grant (the one action with no per-sender verification) requires an interactive y/N on a TTY and refuses non-TTY stdin, the setup command's established discipline; `allow-all --remove` and `allow --remove` are fail-safe directions and run without confirmation. This is also where HCI-2's "explicit confirmation" lives in code and test.
- **Recorded decision — release matches by fingerprint, never by name.** `allow` saves the entry and then releases every held record whose `actor_fingerprint` equals the resolved fingerprint, via the pipeline's own `heldClear` per (room, seq) — D13 kept intact at the CLI layer (a reused name inherits nothing; a record with a null fingerprint is never matched). `--remove` only removes the entry: held records are pending decisions, not ingested text, and FR-10's "affects future ingestion only" makes touching them a violation.
- **Recorded decision — the point-read seam re-applies the untrusted envelope.** The cached body artifact is what the delivery pipeline withheld (for a foreign sender, the envelope-wrapped text). The CLI's seam fetches the page raw and wraps it with `applyUntrustedEnvelope(page, keypair.fingerprint)` before `heldBody` extracts the row — the same transform the api-client's `readMessage` applies — so the recovered preview byte-matches the cached copy and the preview never silently downgrades the framing the plugin enforces everywhere else (spec-3-3's recorded decision, honored at the new consumer).

## Design Notes

**Why the unbound session is the story's quiet cornerstone.** Every other design choice here is downstream of one fact: the human runs trust commands while the agent session is live, and the session registry frees a name only when its lease dies — a CLI that bound the configured Chat ID would deadlock the exact workflow it exists to serve. The wire already separates authentication (whose key is this? — `POST /api/auth/local`, which needs no name) from identification (what are you called? — `POST /api/session`), so the CLI simply refuses to answer the second question. Everything falls out: no `chat_id_taken` ever, no presence row (the touch no-ops for a session with no live row — `server/api/server.mjs:826-829`), no durable claim pollution, no `config.json` read, and a room-read ACL that admits the CLI session exactly where the installation's own Actor is already a member (same fingerprint). The test proves the property behaviorally: every command runs clean while a live MCP child holds the name.

**Why the preview prints the withheld artifact verbatim instead of "just the text".** The pipeline withheld a specific artifact — for a foreign sender, the envelope-wrapped body with its neutralized terminators. Showing the human anything else (the raw log text, a re-wrapped variant) would make the preview a different framing decision made by different code, which is precisely the persuasion surface FR-9's lanes exist to control. `heldBody` hands the CLI exactly the cached artifact or the point-read recovery of it; the CLI prints it verbatim between delimiters, with a provenance line saying which path served it (local cache vs recovered by point read). The preview is honest about content and provenance in the same breath — and because the recovery seam re-applies the envelope before `heldBody` reads the row, cached and recovered forms are byte-identical by construction, the property `tests/held.test.mjs` already pins and the CLI test re-pins end-to-end against the real server.

**Why resolution refuses instead of guessing, and why `--fingerprint` must be a candidate.** HCI-4's rule is "candidate fingerprints + last-seen presentation and disambiguation flow; never a silent guess", and the AC makes it exit-non-zero-testable. The two-source merge (held records, presence) makes ambiguity a normal state — one name, two keys, exactly D13's scenario — so the ambiguous branch lists each candidate with its fingerprint and where the CLI saw it (held record / presence last-seen), writes nothing, and waits for `--fingerprint`. Requiring the chosen fingerprint to be among the candidates closes the last guess-shaped hole: a typo'd or stale fingerprint can never allow a key that has nothing to do with the name the human typed, and the refusal re-lists the candidates so the flow recovers without re-consulting anything.

**Why `allow-all` is the confirmation-bearing command and `allow` is not.** FR-10 names `agent-room allow <chat-id>` a "one-step human release" — inserting a prompt would contradict the ratified contract, and the command's blast radius is one key. Accept-all is the opposite: it delivers every future sender with no per-sender verification, the one branch the trust matrix labels Instructed precisely because nothing code-visible stands behind it. So the explicit confirmation (a real TTY y/N, refusing pipes and CI exactly as setup refuses them) attaches to the blanket grant, making HCI-2's "explicit confirmation" a code-enforced, test-pinned property of the single action that needs it — and `--remove` variants stay prompt-free because holding messages again is the fail-safe direction.

**Why the dispatch table matters beyond this story.** The `agent-room` bin is one entrypoint serving two future populations: the plugin-side commands (this story: held/allow — PLUGIN_DATA state, session-scoped reads) and Story 4.2's operator family (invite/ban/capacity — in-process core calls on the server host, AD-13). Building `main()` as a command table with per-command `run*` functions (injectable deps, structured outcomes, one coded-error printer) means 4.2 adds entries without touching this story's bodies, and the help text, exit-code discipline, and honesty statement stay single-sourced. The extraction of `http.mjs` serves the same goal: the setup command's battle-tested bounded round-trip becomes the shared CLI substrate instead of a private copy.
