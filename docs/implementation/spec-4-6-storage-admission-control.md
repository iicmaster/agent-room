## Intent

**Problem:** `docs/epics.md:494-505` (Story 4.6) requires the last silent death of a realm: a full disk. The substrate is ready — the store's append path commits inside one `BEGIN IMMEDIATE` (`server/store/room-log.mjs`), FR-17's six-status set is complete with `storage_low` wired by name but never triggered (`server/constants.mjs:102-104` declares the reserves the moment this story consumes them), the operator CLI host from Story 4.2 takes command families by the same JSON-lines grammar (`server/cli/agent-room.mjs`), and the harness convention of "the harness is its child's operator" already exists for the 4.4 gate floors. Nothing watches free space: a send against a full disk dies as a raw SQLite error or, worse, as an `outcome_unknown` the client retries forever; the operator has no capacity view; and the backup/restore + disk-expansion procedure FR-22 demands exists nowhere.

**Approach:** one mechanism, three faces, one guide. The mechanism is a single `statfs` of the data directory (`statfsSync(...).bavail * bsize` — blocks available to unprivileged writes, not `bfree`) against two operator-tunable capacity RESERVES, `STORAGE_WARN_FREE_BYTES` (1 GiB) and `STORAGE_REFUSE_FREE_BYTES` (256 MiB), declared once in `server/constants.mjs` (AD-9). Face one is the store: the admission gate rides INSIDE `appendMessage`'s existing `BEGIN IMMEDIATE`, ordered after the idempotency lookup and the duplicate gate and immediately before the insert, so a refusal and the insert it guards share one serialization point — below the refuse reserve a NEW append throws the coded `storage_low` and the transaction rolls back having written nothing, while exact retries, duplicate drops, and every read resolve from reads alone and never touch the gate; the disk-full write the gate's observation raced (`SQLITE_FULL` at insert or commit) maps to the same coded refusal after the rollback. Face two is the send route: the store's coded refusal is answered as the 200 RESULT `{status: 'storage_low'}` — the FR-17 status's explicit, never-acknowledged face, matching `duplicate_dropped`'s result shape, so the sender learns the exact attempt did not commit without an error envelope inviting retries against a full disk. Face three is the operator: `agent-room capacity` joins the Story 4.2 CLI host (review MED-1 — no new entrypoint), opens NO store (it is a filesystem-and-configuration view that answers even when the store file cannot open — precisely when an operator needs it), and reports the data directory against the same reserves through the same resolution the append path uses, so the command and the gate can never disagree about which side of a reserve a byte count is on. Between the reserves the server emits a warn line at most once per `STORAGE_WARN_INTERVAL_MS` (60 s) — a hint an operator must be able to read, not one line per append. The free-space source, the warn sink, and the clock are injectable at every layer, so tests simulate full disks without filling one; the real filesystem is proven in its own row. The operator surface is `startServer` overrides (validated at startup) plus the two `AGENT_ROOM_STORAGE_*` env knobs for the direct launch (strict per-knob parsing, warning fallback — never a blocked boot), and the shared documented surface between the CLI and a launched server is the env. FR-22's guide is `docs/self-hosting-storage.md`: the reserves, the backup procedure, the restore procedure, disk expansion, and the failure modes.

## Boundaries & Constraints

**Always:** keep the gate inside the store's append transaction, after the idempotency lookup and the duplicate gate and immediately before the insert — refusal is admission control over work that would actually write, and "refusal never drops or alters accepted work" is structural, not a promise; leave reads ungated everywhere (whatever storage can still serve, the log serves); answer the refusal on the wire as the 200 result `{status: 'storage_low'}` — an uncommitted message is never acknowledged, and the outcome-unknown discipline is untouched (the sender saw an explicit answer); map the raced disk-full write (`SQLITE_FULL`) to the same coded refusal after `withImmediateTransaction`'s rollback; keep thresholds capacity reserves, never retention quotas — this module has no delete verb and the log is append-only by construction; declare the reserves and the warn interval once in the constants module and import by name everywhere (AD-9); rate-limit the warn to one line per interval per store connection on the append's own clock; make the free-space source, warn sink, and clock injectable at the gate, the store, and the server, and prove the real `statfs` mechanism against the live filesystem in its own test; validate thresholds at open/startup (non-negative safe integers, refuse ≤ warn — refusing above the warn line is a contradiction) and parse env per-knob with a warning fallback that never blocks a boot; keep `capacity` on the Story 4.2 host with the JSON-lines grammar and the host's exit-code discipline (0 admit, 1 refuse-or-unstatable, 2 usage); keep the CLI and the gate on one thresholds resolution so they cannot disagree; write the backup/restore + disk-expansion guide as honest procedure, not archaeology; test against real servers and the real store, with the full disk simulated through the injectable source.

**Block If:** a refusal (or a disk-full write) is ever acknowledged — a committed-shaped answer to an uncommitted send — halt; FR-22's first consequence. A refusal drops, alters, or re-sequences accepted work — halt. A read is refused because writes are refused — halt; "reads continue wherever storage can serve them." The gate fires for an exact retry or a duplicate drop — halt; they resolve from reads before the gate. The gate fires outside the append transaction — halt; a refusal and its insert must share one serialization point. A threshold literal appears outside the constants module — halt; AD-9. A retention/delete behavior appears — halt; reserves are admission, not quotas. `capacity` opens the store or answers only when the store is healthy — halt; it must answer precisely when the store cannot. A second warn line inside one interval — halt; the warn is readable or it is nothing. An env junk value blocks the direct launch — halt; warn and fall back. A malformed `startServer` override boots — halt; overrides fail startup coded.

**Never:** do not gate the read paths, presence, claims, sessions, or the viewer (appends only); do not add a delete/prune verb (retention is nobody's job here — reserves never age work out); do not register new wire fields or error codes (`storage_low` and the status result shape exist; the spine amendment is additive prose only — the frozen vocabularies gain nothing); do not open the store from `capacity`; do not statfs more than once per append or put the gate behind a timer (the observation must share the transaction's serialization point); do not warn per append; do not let the CLI's thresholds resolution diverge from `openRoomLog`'s; do not tune the declared default reserves inside tests (override through the declared surfaces — the defaults are the operator's contract); do not skip, `.only`, or todo anything; do not claim TLS/remote deployment guidance (Story 4.7's guide owns the TLS paths — this story's guide owns storage only).
