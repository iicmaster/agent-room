## Intent

**Problem:** `docs/epics.md:309-318` opens Epic 2 with the promise that a crash is a non-event: after a SIGKILL and restart, every acknowledged message is readable, room-local sequences continue without reuse or gaps, and the survival matrix holds for everything that exists by this epic — logs, reply links, durable claims, realm_id, broadcast/direct rooms — with client cursors remaining valid across an ordinary restart. The Epic-1 substrate claims every one of these properties in code (WAL + `synchronous=FULL` with ack-after-commit, room-local `MAX(seq)+1` inside `BEGIN IMMEDIATE`, durable `chat_id_claims`/`realms`/`rooms` tables, convergent boot, client-owned cursors), and the store-level crash-before-commit case is already proven (`tests/store.test.mjs:317-451`). But nothing anywhere proves the claim at the level the criterion is written: kill a **live server process** carrying acknowledged traffic, restart it, and show nothing was lost. The Story 1.8 checkpoint explicitly stops short — its world kills the server only during cleanup, and with SIGTERM, not SIGKILL. If any layer between the HTTP acknowledgment and the fsynced WAL were wrong — an acknowledgment sent before commit, a bootstrap that mints a second realm, a sequence allocator that reuses a seq — every test in the 310-test suite would stay green.

**Approach:** one new zero-mock integration test, `tests/integration/restart-survival.test.mjs`, mirroring the Story 1.8 harness discipline (real spawned server children, real MCP stdio children, oracles built in the test file, read-only SQLite inspection): spawn a real server, drive acknowledged traffic through three real MCP children (broadcast sends, a Direct Room with a reply link), advance the client cursors with reads, **SIGKILL** the server immediately after the final acknowledged send — nothing between the ack and the kill — snapshot the durable state read-only from the crashed file, spawn a second real server child on the same data dir, and prove the survival matrix through the surviving clients and read-only inspection — every acknowledged message readable byte-matching, sequences continuing at 3 (no reuse, no gaps), reply links intact in both directions across the restart, realm_id and Broadcast Room stable, pair rooms re-open to the same id, durable claims resolving an offline Actor, the DM ACL still denying a third Actor, and client cursors resuming without re-delivery or reset. Plus one documentation task: fill the seeded TODO entry for 2.1 in the AC evidence file. **No production change is planned**: every survival property this story asserts already has a code home (see Code Map); the story exists to convert those claims into executable proof. If any assertion fails, that is a durability defect to surface and halt on, not a test to soften.

## Boundaries & Constraints

**Always:** kill with a real `SIGKILL` against the real spawned server child (uncatchable — no shutdown handler, no `runtime.json` unlink, no clean WAL close), and only after every send in the traffic batch has returned its acknowledgment, with the final ack and the kill adjacent so zero-idle time exists for any lazy flush — which means every cursor-advancing read, permission check, and file capture runs BEFORE the final send, and no read, snapshot, or capture of any kind runs between the final acknowledgment and the kill (any statement in between is a masking window in which a hypothetical ack-before-commit could complete undetected); take the durable SQLite snapshot READ-ONLY FROM THE CRASHED FILE AFTER THE KILL — the file is readable read-only at that point (the final commit completed, so the WAL index the crash left is valid), a read-only connection can never recover, checkpoint, or tidy the crash, and a snapshot taken through the live server before the kill could never catch an acknowledgment that preceded its COMMIT; restart on the **same** data directory and poll `runtime.json` until it names the **new** server child's pid before any client call, never requiring the killed server to have shut down gracefully (a stale record naming the dead pid is the expected state when S2 starts, and no client call may happen in between or `ensureServer` would judge the record stale and boot a detached sibling); prove survival through the real surfaces — surviving MCP children for sends/reads/opens, read-only `node:sqlite` for raw bytes and row-level oracles — with zero mocks, stubs, or doubles of any kind; run every post-restart survival assertion under a failure wrapper that re-throws with the FULL SQLite rows of every durable table appended to the message (the Block If's rows-at-failure requirement); build every expected value as a literal in the test file, never from a production helper, so a producer regression cannot make both sides drift together; keep every temp directory under `mkdtemp` outside the repository with a `t.after` cleanup that reaps both server children and all MCP children before removal, and discovers/reaps any unexpected server bound to the world's database or port; bound every wait with a deadline and poll, never an unbounded await; assert the exit `signal` is `SIGKILL`, that `runtime.json` and the `-wal`/`-shm` sidecars survive the crash, and that the database file's dev/ino identity is unchanged by the restart (in-place recovery, not recreation); fill the seeded 2.1 entry in the AC evidence file with the exact test title and a note stating what the evidence does **not** prove.

**Block If:** any survival assertion fails — an acknowledged message is unreadable or byte-differs, a seq is reused or gapped, a reply link is lost, `realm_id` changes or a second Broadcast Room appears, a pair room re-opens to a different id, a durable claim is missing, or a cursor re-delivers history or resets — halt with the failing assertion and the SQLite rows; this is a durability defect in the substrate, not a test correction, and it must not be made green by weakening an oracle, adding a checkpoint/fsync/WAL call, or changing the kill to a graceful shutdown; the reconnection path cannot be exercised because `ensureServer` boots an unexpected sibling server — halt with the process inventory (`ensure-server.mjs:247-276` is the exercised decision, and a sibling means the restart ordering or the staleness contract is broken); SIGKILL/recovery proves flaky across repeated runs on the implementation host — halt with the failing run rather than retry-until-green; or making the test pass would require touching any production module — halt and surface the defect in the story result instead, because the epic's thesis is that nothing is lost with the code as it stands.

**Never:** do not modify any production module (`server/**`) — this story adds proof, not behavior, and every property it asserts already has a code home; do not use SIGTERM, `server.close()`, or any graceful path in the kill step (SIGTERM is what cleanup after the assertions may use, exactly as the Story 1.8 world does); do not delete, rewrite, or "clean up" `runtime.json`, the WAL sidecars, or the database between the kill and the restart — a tidied crash proves nothing; do not reset or rewrite any `cursors.json` fixture — the cursor files must carry across the restart untouched until a real read advances them; do not import production modules to compute expected values (the Story 1.8 header discipline: literal oracles built in the test file); do not touch the retired v0.1 files (`server/database.mjs`, `server/roomd.mjs`, `server/daemon-client.mjs`) — the open retro action item `epic-1-retro-item-3` assigns their fate to the migration story (2.3), not this one; do not assert invite or ban persistence — `docs/epics.md:317` (review B1 fix) assigns those to their owning stories 4.2/4.5 and the integrated drills; do not kill mid-request or assert in-flight send resolution — outcome-unknown resolution by idempotent retry is Story 2.5's drill, and this story's oracle is the acknowledged set (the scoping is deliberate and recorded in the Spec Change Log); do not assert presence survival — live sessions and the live Chat ID registry are in-memory by design (`server/api/server.mjs:100-115`) and rebuild on reconnect, so their erasure is correct behavior, not loss; do not modify `tests/integration/first-conversation.test.mjs` or any other existing test file; do not add constants to `server/constants.mjs` — harness budgets live in the test file, as in Story 1.8; do not add a skip, `.only`, or todo path, and do not weaken an assertion to make a host-specific check pass.

## Spec Change Log

### 2026-09-28 — review amendment: kill adjacency, post-kill snapshot, observable-contract wording
- **Resolved the plan's internal contradiction between Task 2's original ordering and the SIGKILL row's adjacency requirement.** The original Task 2 sequenced traffic → reads → SQLite snapshot → cursor captures → kill, while the matrix's kill row demanded the kill "immediately after the final acknowledged send". The ADOPTED order — now implemented, asserted, and described consistently everywhere in this spec — is: traffic sends → cursor-advancing reads → cursor/database captures → final acknowledged send (bob's DM reply, seq 2) → `SIGKILL` with nothing in between → durable snapshot read-only from the crashed file → restart. Why: any statement between the final ack and the kill (a read, a snapshot, a capture) is a masking window in which a hypothetical ack-before-commit could complete undetected, and a pre-kill snapshot taken through the live server can never catch one at all. The crashed file is readable read-only immediately after SIGKILL (the last commit completed, so the WAL index is valid) and a read-only connection can never tidy the crash, so the post-kill snapshot is both the sharpest ack-before-commit oracle and a guaranteed non-participant.

## Design Notes

**Why SIGKILL is the honest oracle, and why the kill point matters.** SIGKILL is uncatchable: no shutdown handler runs, so `runtime.json` is never unlinked (`server.mjs:905-919` is the clean-close path the crash skips), the WAL sidecars are never cleanly removed, and the next open performs genuine WAL recovery. The kill lands immediately after the final acknowledged send: `synchronous=FULL` fsyncs the WAL on every commit before `withImmediateTransaction` returns (`room-log.mjs:289-313`), so "acknowledged" already implies "survivable" — but that implication is exactly what this story refuses to take on faith. If an acknowledgment ever preceded the commit, the last ack before the kill is where it would show, which is why the kill and the final ack are adjacent — and adjacency is enforced structurally, not aspirationally: every cursor-advancing read, permission check, and file capture runs BEFORE the final send, so nothing at all separates the ack from the kill. Any statement in between would be a masking window in which a hypothetical lazy commit could complete undetected. For the same reason the durable snapshot is taken READ-ONLY FROM THE CRASHED FILE AFTER THE KILL, not before it: a pre-kill snapshot through the live server (or any inspection that waits for a live connection) proves only that a later commit landed. The crashed file is readable read-only at that moment — the final commit completed, so the WAL index the crash left behind is valid — and a read-only connection can never recover, checkpoint, or otherwise tidy what the crash left, so the snapshot is simultaneously the sharpest oracle and a guaranteed non-participant in the crash state. The DM room's seq 2 — bob's reply, whose ack was the kill's immediate neighbor — is the assertion where an ack-before-commit regression must show.

**Why the survival matrix is provable with zero production change.** Each matrix row lands on a structural fact, not a hope: sequences cannot be reused because the allocator is `COALESCE(MAX(seq),0)+1` over durable rows inside the append transaction; reply links cannot be lost because they are FK-constrained columns of the same durable rows; the realm cannot be re-minted because `bootstrapRealm` keeps an existing id and `ensureBroadcastRoom` re-checks inside the write transaction; a pair room cannot re-open as a new room because `UNIQUE(pair_key)` converges both orders; claims cannot vanish because they are committed rows written inside the bind; and cursors cannot be reset by a restart because they are client-owned files the server never holds (`mcp-stdio.mjs:15-19`: "The server holds no per-client delivery state"). The reset notion exists only where re-sequencing invalidates cursor values — the one-time v1→v2 migration, Story 2.3. The test's job is to make each "cannot" bite.

**Why the reconnection row asserts a negative (no sibling).** After the kill, `runtime.json` names a dead pid with an unreachable port — precisely the state `ensureServer` reclaims by booting a replacement. The harness defuses that by letting S2 publish its record first, so the surviving client's recovery path attaches to S2 through the `ready` path. The process inventory then proves the attach happened as designed: if a detached sibling had been booted, there would be two bound pids and the row would fail. This is the same only-one-server discipline the Story 1.8 checkpoint pinned, now exercised across a crash boundary. The recovery chain's internal steps (`api-client.mjs:327-354`) run inside the MCP child and are deliberately not re-asserted here — the zero-mock rule makes them unobservable from this test, and their step-level coverage already lives in `tests/mcp-tools.test.mjs`.

**Why presence is absent from the matrix, and why that is not a gap.** The criterion enumerates what must survive: logs, reply links, durable claims, realm_id, broadcast/direct rooms. Live sessions, the live Chat ID registry, and online presence are in-memory by design and rebuild on reconnect (`server.mjs:100-115` — "a restart clears sessions (Epic 2 owns continuity)"); their erasure is the documented behavior, and the reconnection row proves the rebuild works (re-auth, re-bind, claim re-write). Asserting presence survival would pin the wrong property.

**Why the evidence entry ships with the story.** The Epic 2 section of the evidence file was seeded with deliberate TODOs so "the sweep fails loudly on every story below until each one carries real evidence" (`ac-evidence.yaml:167-169`). Filling 2.1's entry as the story lands keeps that mechanism per-story rather than per-epic, and the sweep's own check — the cited test must exist in the live suite — makes the entry a live pointer, not a memorial. The note field records the boundary honestly: this evidence proves acknowledged-state survival and cursor validity; it does not prove in-flight resolution (2.5), migration behavior (2.3), or endurance (2.4).
