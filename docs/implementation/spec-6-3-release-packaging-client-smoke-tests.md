## Intent

**Problem:** `docs/epics.md:591-600` — Story 6.3, the release gate. Nothing yet proves the SHIPPABLE thing: `claude plugin validate --strict` had passed (Story 1.9), but against a test-time materialization; the claimed clients (Claude Code, Zcode — NFR-2's "candidates become claims") had never smoked the actual artifact; and SM-C1's re-measurement — the PRD's counter-metric guarding the default path ("networked features must never tax the default path") — still referenced only the v0.1 anchor (`docs/v01-baseline.md`, mean 0.352 s). The advisor consensus (`docs/implementation/reviews/epic-6-execution-{agy,luna}.md`) makes this story FIRST in Epic 6: it produces the immutable Release Candidate every later phase pins, and "claimed" must come to mean "proven."

**Approach:** one new gate file, `tests/release-smoke.test.mjs`, whose every row runs against what `scripts/package-release.mjs` OUTPUTS, never the repository tree — that is what makes it a release gate. Five tests: (1) the dual packages materialize DETERMINISTICALLY — two independent packager runs agree byte-for-byte under a metadata-free tree digest (SHA-256 over path-sorted `sha256(path)+sha256(bytes)` folds), so the candidate's hashes are reproducible from the source tree forever; (2) the materialized Claude Code package passes the REAL `claude plugin validate --strict` (the Story 1.9 fail-closed pattern: binary identity established structurally via `--version` product identity plus a real `plugin validate --help` probe, the machine-readable `--json` report asserted — success, strict, empty errors and warnings, and the target naming the materialized manifest and nothing else); (3) the Claude Code smoke INSTALLS the materialized package into a fresh emulated host plugin directory, resolves the installed `.mcp.json` the way the host would (`node ${CLAUDE_PLUGIN_ROOT}/server/mcp-stdio.mjs`, cwd `${CLAUDE_PLUGIN_DATA}` — the Claude-specific env var name exercised, `PLUGIN_DATA` left unset), performs the real one-time `agent-room setup` Chat ID choice by importing runSetup FROM THE INSTALLED TREE with TTY-fixture streams (so the installed CLI, its ensureServer boot of the INSTALLED server entry, the claimable probe, and the 0600 config write are all inside the smoke), and drives one full DM round-trip (Smoke-A → Smoke-B → Smoke-A) through two real MCP children of the installed entrypoint — distinct keypairs/fingerprints asserted, one realm, both agents online in presence, converging pair room, committed sends, and delivery inside the literal v1 untrusted envelope with attribution keeping the chosen display Chat ID; (4) the portable package (the Zcode-class artifact) does the identical round-trip through ITS install contract (`mcp.json`, `${PLUGIN_ROOT}`/`${PLUGIN_DATA}`), with the honest scope recorded in the test output: the real Zcode host is REL-1's evidence; and (5) the SM-C1 re-measurement — five fresh installs of the materialized package, each timing the v0.1 protocol's milestones wall-clock from install start (install → A initialized → A Chat ID chosen → B initialized → B Chat ID chosen → A DM opened → A message sent → B DM opened → B received A's message), asserting zero failed installs, the step-delta rule (the only added steps are the two Chat ID choices; the created/joined pair maps one-for-one onto the direct opens), and the rule's own time comparison: each run's end-to-end minus the two added choice rows' own durations must stay within the v0.1 anchor under a declared noise factor (the gates run inside the parallel suite; the quiet-machine numbers are what the release notes record). The freeze: `docs/release-evidence/v0.2.0-candidate.json` records the git commit, both package tree digests, Node/SQLite versions, the validator identity, and the SM-C1 numbers, with the binding statement that Stories 6.2 and 6.1 pin this candidate.

## Boundaries & Constraints

**Always:** materialize into fresh temporary parents OUTSIDE the repository (the containment assertion runs on the realpath before any packager child is spawned — the package gate's own discipline); judge only materialized artifacts (the smoke installs a fresh COPY of the packager output, never the output itself, never the repo tree); resolve installs by READING the installed manifest and matching the frozen contract literally before substituting placeholders; run the real validator with `AGENT_ROOM_CLAUDE_BIN`/PATH resolution, product-identity and subcommand probes, and a never-skip failure (an unresolvable validator is a host blocker); let the Chat ID choice be the REAL `runSetup` flow from the installed tree (TTY fixtures replace only the keystrokes); reap every process the gate creates — MCP children by close(), the detached ensureServer-booted shared server by its runtime.json pid (inline per SM-C1 run so the five runs never accumulate live servers, and in the world cleanup); assert DM delivery against a literal envelope template spelled in the test file, never a production helper; record every SM-C1 per-run number in the diagnostic output for the release notes and the candidate record; keep the working tree uncommitted.

**Block If:** a materialization is not deterministic (the candidate's hashes could not be reproduced) — halt; `claude plugin validate --strict` fails on the materialized package, or the report is not strict/emptied/targeted as asserted — halt; either client smoke fails any hop (identity, presence, pair-room convergence, committed send, envelope-exact delivery, reply leg) — halt; any fresh install fails to reach the first exchanged message, or the exercised ladder's delta versus v0.1's is anything but the two Chat ID choices — halt; the adjusted SM-C1 mean exceeds the anchor's declared noise ceiling (a structural time regression) — halt with the per-run numbers. A reaped-pid leak (any gate process alive after cleanup) is a harness defect — halt.

**Never:** never point any gate at the repository tree as the artifact under test; never hardcode a resolved install path — the installed manifest is the resolution input; never set `PLUGIN_DATA` in the Claude Code smoke (the Claude-specific `CLAUDE_PLUGIN_DATA` var is the contract being proven); never weaken the validator identity probes or accept a shim; never skip, `.only`, or todo a row (the gates never skip — a missing `claude` binary fails the host loudly); never write into the repository during a test (diagnostics carry the numbers out; the docs are frozen by the story, not by the run); never restate a product limit literal (harness budgets only, named as in the package gate).
