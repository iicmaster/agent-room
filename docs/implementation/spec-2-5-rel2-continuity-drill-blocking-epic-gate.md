## Intent

**Problem:** `docs/epics.md` (Story 2.5) makes the REL-2 continuity drill Epic 2's **blocking exit gate**: an external recorder must log every acknowledged (room, seq, idempotency key) while traffic flows, ≥3 randomized kill/restore cycles must execute, and the pass condition is absolute — every acknowledged message readable, room-local sequences contiguous, cursors valid, in-flight sends resolved via idempotent retry with zero duplicates. The second criterion is the gate itself: until this drill passes, Epic 2 is not done, and no clean-restart-only acceptance counts. Stories 2.1–2.4 each deferred something to this story (2.1: in-flight send resolution; 2.2: reconnection during an in-flight long-poll hold; 2.3/2.4 named the drill as the remaining epic gap), and the evidence file still carried the 2.5 TODO. Nothing of the kind existed: no external ack recorder, no randomized kill timing, no drill.

**Approach:** one new drill test, `tests/drills/rel2-kill-drill.test.mjs`, plus one small helper process, `tests/drills/rel2-recorder-child.mjs`, reusing the Story 2.4 leak-tracker unchanged. The drill spawns a real server child, attaches two real `mcp-stdio` children (alice, bob — distinct installations, distinct Ed25519 keypairs) that open the pair room from both sides, and starts two continuous traffic loops (unique `client_message_id` per logical message, alternating Broadcast Room and pair DM, cursor-advancing reads interleaved) that report every acknowledged send to the external recorder. Three kill/restore cycles follow, each against a freshly warmed server instance: a seeded mulberry32 PRNG draws the kill moment inside the sampled traffic window; the live server child is SIGKILLed, the port's death is observed, a fresh child respawns on the SAME data directory, readiness is declared only by a runtime record naming the new pid, and traffic resumes. The last kill cycle is the **strike**: the server is SIGSTOPed for 250 ms before the SIGKILL, so both clients' next sends hang with the outcome unknown and the Story 1.7 outcome-unknown discipline is exercised by construction rather than by luck. After the final traffic window the drill verifies everything against the recorder's file: every acknowledged record readable, per-room sequences contiguous from 1, acked-set equal to the readable-set, zero duplicated `client_message_id` or `(room, seq)`, byte-exact payloads in each reader's own view, cursors that never re-deliver and land exactly at head, and — per instance — the Story 2.4 leak oracles (FD within ±5 of baseline, RSS slope ≤2%/s) behind a stabilization warmup burst. The 2.5 evidence entry is filled with the real test name and an honest note. **This story is Epic 2's exit gate: the epic is not done without it.**

## Boundaries & Constraints

**Always:** spawn real processes only — a real `server/api/server.mjs` child per cycle, real `mcp-stdio` children that survive the server's death and recover through their own machinery, a real external recorder process; keep the recorder OUTSIDE the server (separate Node process, own log file, 0600) so the acknowledged-set survives every kill by definition; derive every kill moment from the seeded PRNG and log the seed (`AGENT_ROOM_REL2_SEED` replays a failure); wait for the port to die before respawning and declare readiness only from a runtime record naming the new child's pid; warm every server instance with a hot burst until its RSS stabilizes before opening the leak-tracker window (the Story 2.4 warm-then-measure discipline — a cold allocator's ramp measured 5%/s and would masquerade as a leak); stop each instance's tracker before its kill so no sample races a vanished pid; make the in-flight row deterministic via the strike freeze; verify with numbers, never vibes — exact set equalities, contiguity arrays, uniqueness maps, byte comparisons, ±5 and ≤2% corridors; keep every budget a local constant of the test file; run the whole drill in one test like the restart-survival checkpoint. **Block If:** the drill can only pass by weakening an oracle (widening the FD corridor, raising the memory tolerance, dropping the acked==readable equality, allowing `.only`/`.skip`) — halt and diagnose; a send that cannot resolve within its deadline, a recorder exit code, a gap in any room's sequences, or a cursor that re-delivers is a real defect — halt; the warmup cannot stabilize a server instance inside its deadline — the window's own assertions fail honestly, never widened; the client wedges on `chat_id_taken` after a restart — that is a production defect (it happened — see Spec Change Log) — halt and fix the client, never retry around it in the test. **Never:** no mocks, stubs, or fakes for the server, the recorder, the sockets, or the identity machinery; no clean-restart-only acceptance (kills must land mid-traffic, and the strike must hang real sends); no unseeded randomness (the same seed replays the same drill); no shared harness rebuilt as a production dependency (the only imported test module is `tests/harness/leak-tracker.mjs`, whose reuse contract this story exists to exercise); no restated AD-9 limit literals (the constants scan bites); no production changes beyond what a drill-exposed defect forces, and only with the existing suites kept green unchanged.

### 2026-09-28 — implementation decisions (recorded during the build)
- **Recorded decision — the recorder is a spawned Node process that OWNS its log file.** "External" is made structural, not notional: the recorder holds no state in the server's data directory, opens no socket, and appends each ack with one `write(2)` (fsync at exit), so the acknowledged-set survives every server SIGKILL by construction. The clients "report" through their driver: the drill's traffic loops see each tool-level acknowledgment and forward `(room_id, seq, client_message_id)` to the recorder's stdin in the same tick.
- **Recorded decision — the memory window needs a per-instance warmup, probed not assumed.** A cold server's RSS ramps for ~8-10 s under hot traffic (probed: 59→102→116 MiB across bursts; a window opened mid-ramp measured 130→166 MiB = 4.8 %/s — a false leak). Each cycle therefore warms its fresh instance with adaptive hot-burst rounds until the trailing least-squares RSS slope flattens (≤0.75 %/s over 5 outside samples, ≥6 rounds, 25 s deadline), then opens the tracker window at the post-plateau baseline. Measured window slopes across runs: −2.54 to +0.48 %/s. The warmup's messages are real drill traffic — unique ids, acknowledged, recorded, verified — so warming cannot distort the oracles.
- **Recorded decision — the strike makes the in-flight row deterministic.** Left to luck, a randomized kill interrupts an in-flight SEND only when the kill instant lands inside the ~1-2 ms send window (measured: 2 resolutions across 4 randomized cycles) — the client's own reconnect loop absorbs most kills invisibly within one application-level attempt. The last kill cycle therefore SIGSTOPs the server for 250 ms before the SIGKILL: responses stop, both clients' next sends hang with the outcome unknown (the request is on the wire; the commit state unknowable), and the SIGKILL tears the hung calls down — so the Story 1.7 outcome-unknown discipline is exercised by construction (measured: 6 application-level retry resolutions per run, ≥2 asserted). All three cycles remain randomized kill/restore cycles — the strike adds the freeze to the third drawn kill moment, it does not replace randomization.
- **Recorded defect and fix — concurrent recovery wedged the client on `chat_id_taken` (~15 s per restart).** First runs wedged after every respawn: with several calls in flight across a kill, EACH recovering call reset the shared attach state (`port = null; sessionToken = null`) and re-authenticated, so two binds of the same Chat ID raced on the fresh server; the first won the live registry, the loser surfaced `chat_id_taken`, cleared the winner's token in its failure path, and every subsequent call re-minted a token it could never bind — measured 14.9 s stall and ~1,500 failed sends per restart (the orphaned live session had to die of old age before the name freed). This is a real api-client defect the drill exists to catch (Stories 1.7/2.2 tested recovery with a single sequential call, where the race cannot fire). Fix: `attachEpoch` bumped on each completed re-resolve+re-auth, a recovering call skips the reset when a concurrent call already recovered on its behalf, the ensure/401 paths share one single-flight `authenticateOnce()`, and the ensure promise tracks settlement so recovery drops only attaches that are not in flight. The 45 reconnection and mcp-tools tests pass unchanged; the drill is the concurrent-path regression proof.
- **Recorded decision — verification reads are viewer-relative.** Each client's drain returns its OWN view: own messages plain, the other installation's inside the frozen v1 untrusted envelope. The byte-exact oracle therefore rebuilds the envelope as a literal of the test file (never imported) and compares each reader's page against that reader's expected text — which also re-proves attribution (chat id ↔ fingerprint) for all 64k messages.
- **Recorded decision — determinism and speed.** The drill is one test so the gate is atomic; the default seed is a file constant (20260928) with `AGENT_ROOM_REL2_SEED` for replay; consecutive-run wall times settled at 71-79 s (a first shape measured 88.9 s under load and was trimmed: kill windows 2.5-4.5 s, stabilization flat-window 5 samples) — inside the <90 s budget with headroom. A cleanup-side `Promise.race` against an uncleared 35 s timer was found holding the process open after green and fixed (timer cleared on win) — the suite must not pay ghost seconds for a drill that already finished.

## Design Notes

**Why the drill is the epic's gate, mechanically.** Stories 2.1-2.4 prove the pieces: the kill boundary with an adjacent final send (2.1), the reconnection schedule (2.2), the upgrade (2.3), the leak harness (2.4). Only the drill composes them under RANDOMIZED kills with traffic flowing and an external acknowledged-set — the one arrangement where "nothing is lost" can fail while every component test stays green (the concurrent-recovery wedge is precisely such a failure: 45 client tests green, the drill red). That is why the criterion's second row is procedural and why this spec states it in the deliverables: until `tests/drills/rel2-kill-drill.test.mjs` is green, Epic 2 is not done, regardless of any other evidence.

**Why the recorder survives "by definition" and why that phrase is load-bearing.** A recorder inside the server (a table, a log through the API) would die with the server exactly when it is needed. A recorder in the test process would still be external to the server but would make "the acked set" a test-local fiction. A separate Node process owning a file the server never touches makes the acknowledged-set a fact about the world, not about the harness — the drill can then say "nothing lost, nothing phantom" as a set equality between two independently-produced collections: the recorder's file and the server's drained log.

**Why warm-then-measure is repeated per instance, and why that is honest.** The drill restarts into a cold allocator three times; each restart re-arms the ramp Story 2.4 documented. Skipping the warmup would make the ≤2%/s rule measure V8 and SQLite cache growth, not leaks — probed, a window opened 2.5 s into a fresh instance's life read 4.8 %/s and failed with RSS 130→166 MiB. The adaptive burst (rounds of 800 unpaced sends until the instance's own trailing slope flattens, sampled through the harness's point sampler) opens every window at the plateau: measured slopes +0.09 to +0.19 %/s. The warmup cannot mask a real leak: its messages are drill traffic through the same path, and a genuine per-message retention would still slope the window upward — the burst only removes the allocator's own ramp from the measurement.

**Why the strike is not cheating the randomization.** The criterion asks for ≥3 randomized kill/restore cycles AND for in-flight sends to resolve via idempotent retry. Randomized kills produce in-flight-send interruptions only stochastically (measured 2 across 4 cycles — the client's reconnect loop resolves most kills inside one application attempt). The strike keeps the kill moment seeded-random inside the sampled window and adds a freeze so the interruption is certain; nothing about the pass conditions changes — the same oracles judge the same recovery path, just invoked on every run. A blocking gate that exercised its core row only when the PRNG cooperated would be a gate that could pass green while the discipline regressed.

**Why the concurrent-recovery fix belongs to this story.** The wedge is unreachable by any single-call test: it needs ≥2 calls in flight across a kill — exactly the drill's shape. Leaving it unfixed would force the drill to retry around `chat_id_taken` with NEW ids, which would poison the zero-duplicate oracle (a phantom row per wedge) — the drill would have to lie to pass. Fixing the client (coalesced recovery) is the only shape in which the drill's oracles can be honest, and the fix is deliberately conservative: the wire contract, the single-call recovery semantics, the bind refusal for genuinely different live sessions — all unchanged, with the 45 existing client tests green as the guard.
