## Intent

**Problem:** `docs/epics.md:447-459` (Story 4.2) requires the membership half of Epic 4: atomic, race-safe invite enrollment run through a real operator CLI. The substrate Story 4.1 left is exactly the reserved seam — `POST /api/auth/enroll` is the one frozen route still unregistered (`server/api/routes.mjs:70`, pinned 404-unregistered by `tests/api-host.test.mjs`), the durable `enrolled_actors` table exists with the local exchange as its only writer, and the challenge-answer gate means an enrolled key can immediately mint sessions while nothing can yet ENROLL a remote key. There is also no operator CLI host: the `agent-room` bin carries the human trust surface (Story 3.4) but no invite grammar, no JSON-lines output discipline, and no stable exit-code contract — and Stories 4.5 (ban) and 4.6 (capacity) are waiting to add commands to exactly one host (review MED-1). FR-14's whole discipline is unimplemented: no token shape, no digest-only persistence, no finite-only flags, no atomic consume, no 5/min/IP admission gate.

**Approach:** two halves over the existing single-writer store. (1) The store gains an `invites` registry plus its `invite_consumptions` ledger through the additive open-path convergence (the `enrolled_actors` pattern, no `user_version` bump), with a new `server/store/invites.mjs` owning the DDL, the token/digest derivation, and the operations; `room-log.mjs` wires them in with ITS OWN `withImmediateTransaction` runner, so `enrollRemoteActor` is ONE BEGIN IMMEDIATE: validate invite (exists, unrevoked, unexpired) → verify the possession proof → reattach check → consume (insert consumption, decrement uses, INSERT `enrolled_actors` DO NOTHING). A token is `ar_inv1_` + exactly 43 base64url chars (32 random bytes); only the SHA-256 digest of those 32 bytes is ever persisted, so mint's single stdout line is the token's only appearance in the universe. The possession proof binds the invite presentation itself: the presented raw key must have Ed25519-signed the exact presented token bytes — the invite secret IS the challenge, which fits the frozen enroll field set (`invite_token`, `public_key`, `signature`, no nonce field to carry a 4.1-style challenge) and makes a captured signature enroll nothing else. (2) The operator CLI host is established in the shared `agent-room` bin: `invite mint` (token printed exactly once; `--uses`/`--ttl` finite-only — the store itself accepts no unlimited spelling), `invite list` (digest prefix + uses remaining + expiry + revoked, never a secret), `invite revoke <digest-prefix>` (>= 12 hex chars, ambiguous prefix refused with candidates). The family opens the store DIRECTLY (AR-13: the host boundary is the operator; no HTTP, no session, no server required) and speaks JSON lines with stable exit codes — 0 ok, 1 refusal, 2 usage — HCI-3's grammar. The route registers with the possession-deriving handler, paced by a minimal fixed-window limiter (`server/api/enroll-rate-limit.mjs`) living in the budgets STAGE (never the handler, AD-7), keyed by client identity where `X-Forwarded-For` is honored only under the explicit `startServer({ trustedProxy: true })` configuration.

## Boundaries & Constraints

**Always:** keep the enrollment transaction atomic — invite validation, possession proof, reattach check, consumption decrement, and the `enrolled_actors` insert live in the one BEGIN IMMEDIATE the store's transaction runner executes, so a failed or rolled-back attempt consumes nothing and exactly one contender commits (single writer, AR-2); derive identity, never accept it — the enrolled fingerprint is SHA-256 over the presented raw key, and the route's frozen field set admits no fingerprint field to forge; persist only the digest — no write path in the invites module accepts token material, and every listing projects the digest PREFIX; verify the possession proof BEFORE any consumption write; keep mint's flags finite-only at BOTH layers — the CLI parser rejects any non-digit/non-finite spelling outright and the store accepts no implicit default; keep the raw token to exactly one surface (the mint receipt line) and sweep every other surface (listings, revocations, refusals, diagnostics) with a counted scan; make refusal exits stable (0/1/2) and every output line valid JSON; rate-limit only the enroll route, in the budgets stage, counting at admission, with zero state on refusal; honor forwarded addresses only under `trustedProxy === true` (default OFF — spoofing cannot mint buckets); import every bound by name from the constants module (`INVITE_TOKEN_*`, `INVITE_DIGEST_PREFIX_CHARS`, `ENROLLMENT_PER_MINUTE`, `ENROLLMENT_WINDOW_MS`); register the four new codes once each in `PUBLIC_ERRORS`/`PUBLIC_ERROR_STATUS`; amend the spine additively with dated prose placed where the live-spine parsers cannot misread it; test over real processes — the race is two real children on their own SQLite connections, the journey row runs a real spawned server child, and every CLI row drives the real dispatch.

**Block If:** two racing enrollments both commit, or a loser consumes a use — halt; the single-writer transaction is the story's spine. A raw token (or its payload) appears in any database byte, listing, error, or diagnostic — halt; digest-only is FR-14's redaction rule. An enrollment commits without a verifying possession proof, or a failed signature burns a use — halt. Any mint path accepts an unlimited or never-expiring spelling — halt; the finite-only rule rejects outright. An operator HTTP route appears, or the API can mint/revoke — halt; AR-13. The enroll limiter gates any route other than `/api/auth/enroll`, or lives in a handler — halt; the story's scope is enroll-only and AD-7 puts gates in stages. `X-Forwarded-For` influences bucket keys without `trustedProxy` — halt. A limit literal or an error status appears outside the constants module — halt; AD-9. A listing prints a full digest — halt; the prefix projection is the AC's letter.

**Never:** do not implement ban, capacity, or any later operator command (4.5/4.6 add to this host); do not touch the challenge/answer routes' behavior or the local path (one session mechanism, AD-5 — enrollment only writes the row the answer gate reads); do not add a session-token issuance to the enroll route (the answer route already owns minting; enrollment just unlocks it); do not change `SESSION_TTL_SECONDS`, the trust matrix, the viewer, or the MCP surface; do not bump `user_version` or touch the v1 migration's own table set (the additive convergence runs at open, exactly like `enrolled_actors`); do not restate a fingerprint definition or a bound; do not skip, `.only`, or todo anything; do not commit.

## Design Notes

- **Why the CLI opens the store directly.** AD-13 names the operator boundary: "the operator is the OS user who runs the server process... No operator routes exist." The held/allow family talks HTTP because it is the PLUGIN's human surface inspecting server-held trust state; the invite family is the SERVER HOST's surface over the host's own store. Opening the store directly means no session token is involved, no server must be running, and there is no second path to keep in sync with the route's semantics — the CLI and the route call the SAME `enrollRemoteActor`/`mintInvite`/`revokeInvite` code. The family module contains no HTTP client at all, and a structural test pins that.
- **Why the digest, and why the digest is enough.** FR-14's rule — "SHA-256 digest stored, raw token shown exactly once" — only works if no code path can ever need the token again: consumption is keyed by the digest of the PRESENTED token (recomputed on every presentation, never looked up from storage), listings project a 12-hex prefix of the digest (48 bits — collision-proof at operator scale, and a one-way derivative besides), and revocation matches by prefix. The counted scans prove the token and its payload appear in no database byte and no output byte beyond the single mint receipt.
- **Why the signature covers the token rather than a nonce.** The frozen field set decided this before implementation did: `signature` with no `nonce` means the signed material must be something both parties already hold — the token. Signing the exact presented token bytes proves (a) possession of the private key matching the presented public key, and (b) that the proof was made FOR this invite — a captured `{token, public_key, signature}` triple can be replayed only as the idempotent reattach of the SAME key (which consumes nothing), never as a fresh enrollment of an attacker's key, because the attacker cannot produce a signature over the token under THEIR key that verifies. This is the same consume-first/no-grinding spirit as 4.1 with strictly less state.
- **Why `invite_exhausted` is 409 and `invite_invalid` is 403.** Exhaustion is a conflicted state: the request was well-formed and the invite real, but another writer won the race — 409, like `chat_id_taken`. An unknown, revoked, or expired token is a credential-class failure — 403, like `not_enrolled`, even though the request shape was fine.
- **Why the reattach precedes the exhaustion check.** Order inside the transaction: a key that already consumed this invite must succeed even when `uses_remaining` is 0 — that is the whole lost-response retry property on a single-use invite. A DIFFERENT key past zero uses is the race loser. Swapping the order would strand the honest retry behind the loser's error.
- **Why a fresh limiter per server instance.** The session/challenge registries are process-shared deliberately (one host process = one local-mode topology); rate buckets are per-realm admission state, and a shared counter would let two servers in one test process fill each other's budgets. `startServer` therefore constructs its own unless the caller injects one — the same default-plus-override pattern, with per-instance defaulting.
- **Why the fixed window is enough for this story.** "5/min/IP burst 5" with a fixed 60 s window and a limit of 5 admits all five instantly (the burst) and refuses the sixth until the window rolls — exactly the declared behavior, with no token-bucket timer machinery. The window and the limit are imported by name; if a later story splits the pair, Story 4.4's budget stage owns the general mechanism and this module remains the enroll route's minimal admission gate.
- **Why the spine amendments are prose, placed where they are.** The live-spine contract test extracts route triples from `- **class:**` bullet lines and field names from the frozen-vocabulary sentence. The 4.2 amendments are plain paragraphs — the enroll-fields amendment after the send-semantics sentence, the AD-13 amendment after the rule bullet — so the parsers cannot misread amendment prose as routes or vocabulary, and no amendment text needed stripping rules.
