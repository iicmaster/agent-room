## Intent

**Problem:** `docs/epics.md:484-492` (Story 4.5) requires the operator's power to remove a bad Actor: ban a key and have it stick immediately. The substrate is exactly the reserved seams — the pipeline's authz stage is a structural pass-through (`server/api/pipeline.mjs`), the FR-17 send-status enum carries `banned` wired by name but never triggered (`server/constants.mjs:186-193`), Story 4.2's operator CLI host takes command families by one JSON-lines grammar with stable exit codes (`server/cli/agent-room.mjs`, review MED-1: later operator stories add commands, never entrypoints), and the Epic 2 review's B1 boundary explicitly deferred invite/ban persistence proof to their owning stories (4.2/4.5 — the survival matrix's ban row is proven here, finally). Nothing could refuse a key: a malicious Actor could be re-enrolled forever, and no operator verb existed to stop one.

**Approach:** one durable registry, three enforcement faces, one operator surface — identity is the key, never anything the client presents. The registry is `banned_actors` (STRICT, `actor_fingerprint` PRIMARY KEY, additive open-path convergence with no schema-version bump, column-set verification refusing a divergent shape as a coded `database_schema_invalid`): one row per banned identity key, keyed by the canonical fingerprint (`sha256:` + 64 lowercase hex — the constants module's single pattern, the retro's collapse action), with **no foreign key into enrolled_actors because a PREEMPTIVE ban of a never-seen key is first-class** — the ban is about the identity, and must precede the identity's first appearance. Face one is the per-request gate: the authz stage queries the registry directly (one indexed SELECT on the request's own store connection) for EVERY actor-class route and refuses the coded `banned` (403 — the send-status code's wire face, registered once in the constants module like `rate_limited` before it) before any handler runs; the check is **deliberately NOT a cached set**, because the operator CLI is a separate process writing the same SQLite file, and only a per-request WAL read can make a ban visible "at next request" — there is no ban state in memory to go stale. Face two is the two paths the stage cannot cover: the long-poll read loop re-checks the gate on EVERY poll iteration (the wake is never more than `LONGPOLL_POLL_INTERVAL_MS` = 250 ms away), so a ban landing mid-hold terminates the in-flight poll at its next wake — well inside the 20 s window (`READ_HOLD_MAX_MS`), the registry the poll already checks, never a killed connection; and re-enroll is refused INSIDE the enrollment transaction, AFTER the possession proof verifies (ban state leaks to no caller who cannot prove possession) and BEFORE the reattach check or any use is consumed — every re-enroll from a banned key, including the lost-response reattach retry of a pre-ban enrollment, is a `banned` refusal that consumes nothing. Face three is the operator: `agent-room ban <fingerprint> [--reason <text>]` and `agent-room unban <fingerprint>` join the Story 4.2 host — the same bin, the same dispatch, the same JSON-lines grammar (one line stdout, exit 0; one coded line stderr, exit 1 refusal / 2 usage) — opening the store directly, in process, on the server host (AR-13: no operator HTTP route exists; authentication is the OS user). Idempotence is the operator's intent made durable: re-banning keeps the FIRST ban's timestamp and reason, unbanning a key that holds no row is already the requested state, and unban deletes the row so traffic flows again the moment the delete commits. Persistence — the B1 boundary — is structural (a durable table) and proven at two depths: close-and-reopen at the store, and a full server restart driven by a real CLI child write → SIGKILL → respawn → refusal.

## Boundaries & Constraints

**Always:** key every ban by the canonical Actor fingerprint — the identity the ban is ABOUT (`sha256:` + 64 lowercase hex from the constants module's single `FINGERPRINT_PATTERN`), never a chat id, claim, or presented name (attribution is not identity); read the registry per request on the request's own store connection — a direct indexed query, never a cached in-process set, so a ban the separate CLI process commits is visible at next request through WAL; scope the stage gate to the actor class (the session-authenticated surface — every send, read, session, presence, and enumeration request) and answer the coded `banned` (403 from `PUBLIC_ERROR_STATUS`, never a per-route status); keep the re-enroll refusal inside the enrollment transaction, after the possession proof and before the reattach check or any consumption, so a banned attempt consumes nothing and reveals ban state to no caller failing the proof; keep the challenge route privilegeless-open and the local credential exchange (`POST /api/auth/local`) unban-gated — the ban holds at the resource boundary, which is also what lets a restarted server's banned client authenticate BEFORE being refused everywhere (the restart proof itself depends on this); re-check the ban on every long-poll iteration, terminating at the next wake (≤ 250 ms), never past the deadline, never by killing the connection; make preemptive bans first-class (no FK into enrolled_actors), re-ban idempotent keeping the FIRST `banned_at` and reason (INSERT … DO NOTHING discipline), unban a row-deleting success that reports `removed` honestly (`false` when nothing was there); store a reason as a non-empty string or NULL — never an empty string standing in for "no reason"; converge the table additively on open with no schema-version bump, verifying the column set and refusing a divergent shape as coded `database_schema_invalid`; run every registry write inside the store's own `withImmediateTransaction` (one BEGIN IMMEDIATE/COMMIT/ROLLBACK discipline for the whole store); keep the operator surface on the Story 4.2 host with its JSON-lines grammar and exit codes (0 ok, 1 refusal, 2 usage), gating argv on the same constants pattern the store's CHECK constraint enforces; write every timestamp through the store's canonical ISO 8601 normalization with the injectable clock.

**Block If:** a banned key's request reaches a handler on any actor-class route — halt; the gate is the authz stage. A ban committed by the CLI process is not visible at the server's next request — halt; that is cached state, and the AC's "at next request" is structural. A long-poll held past its 20 s window with the key banned mid-hold, or terminated by killing the connection — halt; the re-check rides the loop's own wake. A banned key's re-enroll consumes an invite use, reattaches, or creates an enrollment row — halt; the gate fires before any consumption, inside the transaction. Ban state is revealed to a caller who has not proven possession (a wrong-key proof answering anything but `signature_invalid`) — halt; the gate is post-proof by construction. A ban keyed by anything but the canonical fingerprint — halt; identity is the key. A schema-version bump for the table — halt; convergence is additive. An operator HTTP route or an `actor_id` accepted from tool or request arguments — halt; AR-13 and NFR-3. A rate-based or heuristic auto-ban — halt; the operator names the key. A re-ban overwriting the first ban's timestamp or reason — halt; idempotence is the intent made durable.

**Never:** do not cache ban state anywhere in the server process; do not gate viewer, health, or pre-auth routes at the stage (no session identity — pre-auth identity gates live inside their own handlers' transactions); do not gate `POST /api/auth/local` (the resource boundary design — see Always); do not add a ban-list command, a ban reason display surface, or any wire field (the AC names ban/unban; the frozen vocabularies gain nothing — `banned` already sits in `SEND_STATUSES` and `PUBLIC_ERRORS`); do not add a foreign key from `banned_actors` into `enrolled_actors`; do not restate the fingerprint pattern, the status code table, or the hold/poll constants outside the constants module (AD-9); do not let the CLI accept a decorated fingerprint spelling the store's CHECK would refuse (one pattern, both gates); do not skip, `.only`, or todo anything; do not rewrite the landed implementation — this story's delta is the spine amendment and whatever review proves wrong, never silent repair.

## Design Notes

- **Why a per-request read instead of a cached set.** The operator CLI and the server are separate processes over one SQLite file (AR-13). Any in-memory ban set in the server would need an invalidation story across a process boundary that has none — and the failure mode (a ban that "sticks" only after a restart) is exactly what the AC's "at next request" forbids. WAL readers see every committed write, the lookup is a PRIMARY KEY SELECT (the cheapest query the store runs), and the Story 4.4 budget stage already established per-request store probes on the hot path (`findIdempotentSend`), so the cost shape has precedent. The restart test proves the cross-process visibility directly: a real CLI child writes the ban; the running server refuses at the next request.
- **Why the re-enroll gate sits after the possession proof.** Ban state is the operator's secret in a weak sense: revealing "this key is banned" to whoever presents the fingerprint would let anyone probe ban state without holding the key. The proof orders the gate: a caller who cannot sign the invite token gets `signature_invalid` — the same answer any unproven key gets — and only a proven keyholder learns the refusal. Placing it before the reattach check also closes the loophole where a pre-ban enrollment's lost-response retry would reattach around the ban: every re-enroll from a banned key consumes nothing, including that one.
- **Why the local credential exchange is not ban-gated.** The ban's teeth are at the resource boundary — every actor-class route refuses before its handler — so gating the token exchange adds nothing: the banned key authenticates and then cannot bind, send, read, or enumerate. The upside is decisive: the exchange is also how a test driver (and, by the same mechanism, any monitoring surface) re-authenticates a KNOWN key after a restart to prove the refusal — the persistence row depends on it. Gating the exchange would also have made the refusal indistinguishable from a broken bootstrap, the exact "silent death" the epic exists to prevent.
- **Why the long-poll re-check rides the loop instead of killing the connection.** The AC bounds the harm: "not held past its 20 s window". The poll loop already wakes every 250 ms to re-poll the store; one more indexed SELECT per wake terminates a banned hold within ~250 ms of the ban landing — two orders of magnitude inside the bound — while connection-killing would break the HTTP semantics the read contract froze (a deadline return is a normal page, never a dropped socket) and buy at most 19.75 s. The admission-time refusal is separately proven: a fresh poll from a banned key never enters the loop at all.
- **Why preemptive bans are first-class.** The operator's worst case is an Actor whose plugin data was deleted and whose key will re-enroll quietly — the ban must precede the key's first appearance in this realm. A foreign key into `enrolled_actors` would make that row unrepresentable; the registry is therefore keyed by identity alone, and the CHECK constraint keeps the key shape canonical at the storage layer, matching the CLI's argv gate and the session principal — one pattern, three enforcement points, one definition (the retro's single-source rule).
- **Why `banned` is a coded 403 and not a send-route result.** The refusal is not the sender's actionable vocabulary — there is no retry that helps, and the same key hits it on every route, not only sends. The coded-error channel (with the status table's 403) is the actor-equivalent of `actor_not_member`: a credential-class answer, route-wide, never a per-route special case. The `SEND_STATUSES` enum still lists `banned` because FR-17's set describes every way a SEND can end — a banned send ends refused — and the enum's completion in 4.4 wired the name this story triggers.
- **Why a self-exhausted banned key can answer 429 before 403 (review-recorded caveat).** The pipeline order is frozen and doubly asserted (AD-7, Story 4.4): budgets run before authorization. A banned key that has exhausted its OWN request budget or send bucket is therefore answered 429 `rate_limited` before the authz stage can read the registry and answer 403 `banned` — the epics letter's "refused with `banned` at next request" holds unconditionally across routes, sessions, and restarts, but the refusal CODE alternates with the key's own budget state. The ban loses no teeth: the refusal is still pre-handler in every case, and no banned request ever reaches a handler. Reordering was considered and rejected: the stage order is Story 4.4's asserted construction, and putting a per-request SQLite read ahead of the in-memory flood gates would regress the 4.4 design it freezes.
