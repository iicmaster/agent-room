## Intent

**Problem:** `docs/epics.md:505-516` (Story 4.7) demands one honest guide for both TLS paths — "a documented procedure, not archaeology" — and FR-4 (`docs/prds/prd-agent-room-2026-09-20/prd.md:108-115`) defines the two paths: TLS terminated at an operator-managed reverse proxy (one documented Caddy recipe) or standalone native `node:https` with an operator-supplied certificate chain and key, both serving the SAME request handler, the proxy's backend plaintext on loopback only. The remote substrate is complete (challenge lane 4.1, invite enrollment 4.2, remote client 4.3, gates 4.4, ban 4.5, storage 4.6) and the client half of TLS is proven — but only through a loopback TLS front in tests (`tests/remote-client-driver.mjs:113-157`, the Caddy-shape simulation; spec-4-3 recorded the honest scope). Three gaps make the AC's walkthrough unfollowable today: (1) the native `node:https` server path does not exist — `startServer` imports `createServer` from `node:http` only (`server/api/server.mjs:101`, server built at `:1260`) and refuses every non-loopback bind (`:1011-1013`), so FR-4's standalone half has no code at all; (2) no shipped command enrolls an installation with its invite token — the client never auto-enrolls (`server/client/api-client.mjs:504-517`) and the frozen `POST /api/auth/enroll` route is driven only by tests' raw HTTP posts (`tests/invites.test.mjs:330`, `tests/remote-client-driver.mjs:200`), so a human following the guide could not reach enrollment with shipped tooling; (3) the direct launch has no topology surface — it hardcodes the loopback host, an ephemeral port, and the shared data dir (`server/api/server.mjs:1501-1508`), so even the Caddy backend has no documented fixed port to proxy to. And nowhere are the AR-15 pins (the epics review's own finding, `docs/epics-review/review-stories-luna.md:157`): Caddy v2.11.x by name and the MCP stdio spec revision 2026-07-28 (`ARCHITECTURE-SPINE.md:184`) wherever the plugin's MCP surface is described — `README.md:39-51` describes that surface with no pin, and `README.md:11-12` still says "Remote and multi-host rooms are not part of version 0.2," stale against four shipped epic-4 stories.

**Approach:** minimum mechanism, maximum honesty. The mechanism is exactly what the walkthrough needs and nothing more. (1) **The transport:** `startServer` gains one option, `tls: { cert, key }` — the operator-supplied PEM certificate chain and key as content strings. Present, both PEMs are validated at startup (parse the certificate, parse the key, require the pair to match — a mismatch or malformed material is a coded `invalid_argument` BEFORE the listener exists, never a runtime handshake mystery); the server is then `https.createServer({ cert, key }, handler)` wrapping the one existing `handleRequest` callback — "both paths use the same request handler" is structural, not claimed. Absent, the byte-identical `node:http` server of today. The bind rule sharpens rather than loosens: WITHOUT tls the loopback-only refusal stands unchanged (`server.mjs:1011-1013` is pinned, not replaced); WITH tls the operator may bind any host — `0.0.0.0` on a VPS — because plaintext remains loopback-only (AD-11: "plaintext is permitted only on loopback"). (2) **The topology surface:** the direct launch reads `AGENT_ROOM_HOST` (default `127.0.0.1`), `AGENT_ROOM_PORT` (default `0`), and `AGENT_ROOM_TLS_CERT`/`AGENT_ROOM_TLS_KEY` (paths to the operator's PEM files, both-or-neither) — the same direct-launch convention as the four existing `*FromEnv` parsers, with one deliberate divergence: topology knobs are STRICT, because a junk port silently falling back to ephemeral would change where the server is reachable — exactly what the start-boundary AC exists to prevent — so junk fails startup with one coded diagnosable line, exit 1 (matching `startServer`'s own option strictness at `server.mjs:1014-1016` and the 4.6 rule that operator overrides never boot malformed). Reading cert/key by PATH (not env content) keeps secrets out of environments and process listings; the files are read through the bounded regular-file reader and the guide documents 0600 on the key. A non-loopback bind onto the DEFAULT shared data dir draws one stderr advisory line to use a dedicated `AGENT_ROOM_DATA_DIR` — a public realm and the local auto-start must never share one data dir (the spine's one-process-one-realm-one-data-dir rule, `ARCHITECTURE-SPINE.md:40`). (3) **The enrollment step:** `agent-room remote enroll <invite-token>` joins the Story 4.3 remote family (`server/cli/remote-commands.mjs`, review MED-1's host rule — the family that owns every installation-vs-remote-server action). It requires a configured origin (coded refusal naming `remote set` otherwise), signs the EXACT invite-token bytes with the installation key (the frozen route's possession proof — `server/api/server.mjs:364-410`, handler at `:385`: token, raw public key, Ed25519 signature; success returns `{fingerprint}`), POSTs once to `<origin>/api/auth/enroll` over the api-client's default-verification HTTPS transport, and prints one JSON receipt that never echoes the full token. Enrollment consumes nothing on failure (the route's own rule) and unlocks the already-live challenge lane — after it, the client connects with zero further enroll requests (the 4.3 journey's counted negatives). (4) **The guide:** `docs/self-hosting-deployment.md`, sibling of Story 4.6's `docs/self-hosting-storage.md` — prerequisites (the Node floor, a dedicated data dir), Path A the Caddy recipe with v2.11.x pinned by name and explicit proxy timeouts ≥30 s over the 20 s hold, Path B the native `node:https` launch with the operator's certificate responsibilities, the shared enrollment walkthrough (`invite mint` on the server host; `setup` → `remote set` → `remote enroll` on the installation; the MCP client's `message_read` held to the `READ_HOLD_MAX_MS` 20 s bound as the read capture), the start boundary (success = `/health` answering with the port bound; failure = one diagnosable line, non-zero exit), restart-with-preserved-enrollment, key permissions, no-secrets-in-logging, the failure-mode appendix where each of the AC's four failures (certificate issuance fails, port already bound, proxy unreachable, enrollment rejected) names symptom → cause → recovery with no dead ends, and the per-path evidence checklist (enrollment receipt + the 20-second read capture) that makes a walkthrough evidence-comparable rather than judgment-only. The AR-15 pins land in the guide AND in `README.md`'s MCP section (the pin travels wherever the MCP surface is described), the stale Remote line is corrected, and a dated spine amendment records the transport, the topology surface, the enroll command, and both pins. Every guide name is pinned by test so the guide cannot silently drift from the shipped surfaces (the 4.6 precedent, `tests/storage-gates.test.mjs:1298-1317`).

## Boundaries & Constraints

**Always:** serve BOTH TLS paths through the one existing `handleRequest` callback — a second request path is the fork AD-10 exists to prevent; validate the operator's TLS material at startup (parse certificate + key, require the pair to match) and fail coded `invalid_argument` before the listener exists; keep the no-tls loopback-only refusal byte-for-byte (this story sharpens the rule — plaintext on loopback only — it does not erode it); make the direct-launch topology env strict (junk host, junk port, a missing cert/key file, one knob without its sibling → one coded stderr line, exit 1, no stack) and keep the absent-env behavior byte-identical to today's loopback/ephemeral launch; bind the guide to shipped surfaces only — every command in it must exist when the story lands, and the guide-name pin enforces the surfaces' names; state the loopback-only plaintext backend rule, both AR-15 pins (Caddy v2.11.x by name — the guide names the exact 2.11.x release its recipe was executed against; MCP stdio spec revision 2026-07-28), the start boundary, certificate acquisition/renewal responsibility, key permissions (0600), restart-with-preserved-enrollment (enrollment is a durable store row; cursors are plugin-local), proxy timeouts ≥30 s, and no-secrets-in-logging in prose a VPS operator can follow top to bottom; give every failure-mode appendix row symptom, likely cause, and recovery step; scope the automated proof honestly (loopback through real TLS — real certs from the existing throwaway test PKI, `tests/remote-client.test.mjs:63-67`, real child processes, the real driver mechanism `NODE_EXTRA_CA_CERTS`, `tests/remote-client.test.mjs:512-519`) and leave the literal cross-machine proof to Story 4.8; **Block If:** a TLS server answers through anything but the shared handler — halt. Plaintext (no tls) binds a non-loopback host — halt; the rule must survive this story. Any TLS-verification escape hatch appears in new code — halt; AD-11 plus the 4.3 policy. A topology env junk value boots onto a different reachable socket than named — halt; topology is strict, tuning knobs are the warn-and-fallback kind and this is not one. `remote enroll` mutates the enroll route, mints a session itself, or auto-enrolls — halt; the route is frozen (AD-8), the session belongs to the answer lane (AD-5), and enrollment stays the operator's invite flow. A new surface echoes a full invite token or any private key material — halt. The guide documents a command, flag, knob, or file that no shipped surface provides — halt; that is precisely the archaeology the AC forbids. The guide's failure-mode appendix contains a dead end (a failure named without symptom+cause+recovery, or a recovery step referencing an undocumented surface) — halt. The evidence checklist judges instead of evidencing (no concrete artifact named per path) — halt. The MCP pin is paraphrased — halt; `2026-07-28` appears verbatim or not at all. A Caddyfile, systemd unit, or Dockerfile artifact ships in the repo — halt; the spine defers the tooling (`ARCHITECTURE-SPINE.md:224`), the guide documents procedures.

**Never:** do not change any route, request field, response field, status, error code, or constant (the wire is frozen; `READ_HOLD_MAX_MS` 20000 and the enrollment limits are imported by name, never restated — AD-9); do not add TLS options to the api-client or a CA option anywhere (the client's transport policy is Story 4.3's and it is complete); do not touch the local path's behavior — with no env and no tls option the direct launch, `ensureServer`, and every test that exists today are byte-identical; do not implement ban/capacity-style operator commands or any other host family (MED-1: this story extends the remote family only); do not register new MCP tools or touch the viewer (Epic 5); do not implement deployment automation tooling; do not restate a fingerprint definition, a bound, or a version number the guide should cite from the surfaces themselves; do not let the README's MCP description carry text without the spec-revision pin (AR-15); do not enforce 0600 on operator-supplied key FILES (they are not agent-room state — the runtime permission gates stay scoped to agent-room's own state; the guide DOCUMENTS the permission); do not skip, `.only`, or todo anything; do not commit.

## Design Notes

- **Why the story carries code at all (it is "a guide" story).** The AC's letter is a walkthrough that REACHES enrollment + a 20-second read on both TLS paths. Two of the steps have no shipped implementation: the native `node:https` listener (FR-4's standalone half was never built — `server.mjs:101,1260` are `node:http` only) and any enrollment command (the client never auto-enrolls by policy, `api-client.mjs:504-517`, and the route is driven only by test harnesses). A guide documenting nonexistent surfaces would be exactly the archaeology the story exists to end, so the mechanism is scoped to precisely those two gaps plus the fixed-port surface the Caddy backend needs. Everything else the AC names (health boundary, diagnosable failure) already exists and is pinned, not rebuilt.
- **Why `remote enroll` joins the remote family rather than minting a new top-level command.** Story 4.3 established the family as "every installation-vs-remote-server action" and review MED-1's host rule forbids parallel command homes; enrollment is meaningless without a configured origin, which is the family's own state. The command reuses the family's grammar (strict argv, JSON lines, 0/1/2) verbatim.
- **Why topology env is strict where every earlier `*FromEnv` knob falls back.** The four existing parsers tune LIMITS (TTLs, floors, reserves) where a fallback is safe — the server behaves, just with defaults. HOST/PORT/TLS-material are TOPOLOGY: a junk `AGENT_ROOM_PORT` falling back to ephemeral changes where the server is reachable, which is the failure the start-boundary AC (health + bound ports vs non-zero exit) defines as diagnosable, not recoverable. The strictness matches `startServer`'s own option validation (`server.mjs:1014-1016`) and the 4.6 rule that operator overrides never boot malformed.
- **Why the key pair is validated at startup.** `https.createServer` accepts malformed PEM silently and fails at first handshake — a runtime mystery a VPS operator cannot diagnose. Parsing the certificate and key and requiring the pair to match converts the whole material matrix into the coded startup failure FR-4's boundary demands.
- **Why 0600 is documented, not enforced, on the TLS key.** The runtime permission gates protect AGENT-ROOM state; an operator's certbot-managed key is not agent-room state and real ACME tooling uses varying ownership models. The house rule (owner-only state) is preserved by scoping enforcement to agent-room's own files, and the guide states 0600 as the operator's responsibility.
