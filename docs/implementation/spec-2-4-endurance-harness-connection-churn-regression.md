## Intent

**Problem:** `docs/epics.md` (Story 2.4) wants endurance problems surfacing in daily development, not in Epic 6, and pins two executable criteria. First, `tests/harness/leak-tracker.mjs` must exist as an opt-in harness that samples RSS **and** FD counts at 5-minute-equivalent intervals (the test compresses time by choosing its own interval; the RULE is what is pinned) and evaluates the single memory pass rule — least-squares slope ≤2% of starting RSS. Second, a churn regression in `tests/` must run 100 connect/disconnect cycles against a real server and assert NUMBERS — all succeed, FD counts within ±5 of the post-warmup baseline, zero leaked sockets/handles — never "stable" (review M4). Nothing of the kind exists: Stories 2.1 and 2.2's evidence notes both explicitly defer soak/FD endurance to this story, and the suite has no leak-tracking, no descriptor sampling, and no churn row. The harness is also the reuse contract for Stories 2.5, 4.8, and 6.2, so its exports are the deliverable, not an implementation detail.

**Approach:** test-side only — no production module changes. One new harness, `tests/harness/leak-tracker.mjs`, exporting the whole reusable surface: point samplers (`sampleRssBytes(pid)`, `sampleFdCount(pid)`) that read OS inventories only — the current process via `process.memoryUsage().rss` and `/dev/fd` (macOS) or `/proc/self/fd` (Linux); any other pid FROM OUTSIDE via `ps -o rss=` plus `lsof -a -p <pid> -F f` on macOS and `/proc/<pid>/status` + `/proc/<pid>/fd` on Linux — plus a pure least-squares regression (`leastSquaresSlopeBytesPerMs`), the pure pass rule (`evaluateRssSamples`: slope as a percent of the window's starting RSS PER SECOND, pass at or below the tolerance, so the rule is a rate that survives time compression and shrinking RSS always passes), the tracker itself (`createLeakTracker({ intervalMs, tolerancePct, pid })` with non-overlapping timed sampling against real timestamps), and the `assertMemoryPass(tracker)` node:test helper. Its own suite, `tests/harness/leak-tracker.test.mjs`, proves the mechanics before anything trusts them: hand-computed literal slopes, flat/declining pass paths, refusal of degenerate windows, FD counting against real descriptor events (+3 files → exactly +3), and the external macOS path against a real spawned child. Then `tests/churn.test.mjs` carries both AC rows over real processes: the churn regression (one spawned `server/api/server.mjs` child, a real 0600 local-token file and Ed25519 keypair, 100 full connect → authenticate → bind → disconnect cycles at four real `Connection: close` sockets each, FD sampling through the tracker before/during/after, and the numeric oracles: 100/100 wire-asserted cycles, every FD sample within ±5 of the post-warmup baseline, the server's TCP inventory reduced to exactly its one LISTEN socket, zero leaked live sessions in presence, healthy version-stable server after) and the memory pass row (hard unpaced warmup driving the runtime's allocator to its steady-state working set, then a time-bounded paced window under the tracker's timed sampling, asserted through `assertMemoryPass`). The 2.4 entry of `docs/implementation/ac-evidence.yaml` is filled with the real test names and an honest note.

## Boundaries & Constraints

**Always:** spawn the real `server/api/server.mjs` child per test into a fresh 0700 temp world and reap it in ordered `t.after` cleanup (SIGTERM, bounded grace, SIGKILL fallback) — the churn tests own their servers, never a shared one; read readiness only from a runtime record naming the spawned child's own pid with a valid port; derive every credential through the real path (`loadOrCreateLocalToken`, `loadOrCreateKeypair`) and assert the 0700/0600 permission row; drive HTTP with `agent: false` so every request is its own socket (`Connection: close`) — socket churn must be real; wrap every request in a deadline so a hung server fails the test, never the clock; take every RSS/FD number through the harness (never ad-hoc `ps` calls beside it) so one mechanism per tracker makes samples like-for-like; let the tracker sample against REAL timestamps and never overlap samples (schedule the next after the previous completes); make sampler failures loud (a vanished pid during sampling is an error naming the pid, never a zero); warm the server before measuring — FD baselines after churn warmup, RSS after hard unpaced warmup — so the measured window reads steady state, not ramp-up; assert numbers, never vibes (±5 corridor, ≤2% slope, exact counts, deep-equal TCP inventories); keep every budget a local constant of the test file (no new production constants — this story changes no production module); document the rule's units (percent of starting RSS per second) in the harness header so Stories 2.5/4.8/6.2 inherit the same rule, not a re-derivation. **Block If:** the FD corridor cannot hold within ±5 across repeated runs — that is a leaked handle (a real defect in the server or the harness's sampling), not test flakiness; halt and diagnose, never widen the corridor to get green. The memory rule can only pass by lowering the tolerance below the AC's 2% or by measuring a cold server — both are design violations; the tolerance and the warm-then-measure shape are the story's contract. FD sampling cannot be made to work on macOS (this machine) — the harness is the deliverable; halt. A sampler failure is swallowed, retried into silence, or reported as zero — halt; the harness fails loudly. The churn row can only pass with fewer than 100 real cycles or with a stubbed server — halt. **Never:** no mocks, stubs, or fakes for the server, the sockets, the token file, or the keypair — real spawn, real loopback TCP, real files; no production module edits (the AC is a test-side deliverable; `server/` is exercised, never modified); no `.only`/`.skip`/`todo` anywhere; no test sleeps on wall-clock claims about endurance ("runs for 5 minutes" is false — the rule is compressed and the evidence note says so); no sampling through platform-specific one-liners beside the harness (all numbers flow through `tests/harness/leak-tracker.mjs`); no weakening of another story's tests to make room; no runtime dependencies (harness is Node built-ins only, `node:assert` included — it is test-scope).

## Design Notes

**Why the rule is a rate, and why that is the whole reuse story.** "5-minute-equivalent interval" only means something if the RULE survives compression. A slope is bytes per millisecond; expressing it as a percent of the window's starting RSS per second divides out both the window length and the server's absolute size, leaving one comparable number: how fast the process is GROWING, not how big it got or how long anyone watched. That is why the same tolerance (2) and the same harness serve this story's 13-second row and, later, Story 6.3's genuine soak — and why a test may sample every 20 ms or every 5 minutes without re-deriving anything. The pinned unit lives in exactly one production-of-tests place: the harness header.

**Why warm-then-measure is not masking a leak.** The warmup happens BEFORE the baseline sample the regression anchors at; everything the window sees is retention at steady-state allocation. A real leak (retained bytes per cycle) shows up as a positive slope exactly the same way it would in a cold measurement — the warmup only removes the allocator's own ramp from the measurement. The distinction is not academic: probed cold, the healthy server reads 4-10 %/s for its first seconds of hot traffic; probed warm, it reads ±0.3 %/s. The rule stays at the AC's 2% either way; only the honesty of what is measured changes. The FD oracle needs no such warmup because descriptor counts have no allocator ramp — and indeed the churn row's corridor held at zero drift in every probe.

**Why the sampler fails loudly, and why that is a feature of the AC.** The worst failure mode for a leak harness is a silent zero: a sampler that returns 0 on a vanished process would make a crashing server look like a leak-free one, and a sampler that swallows errors would make a broken harness look like a pass. Every sampler path therefore distinguishes "the process is gone" (throw, naming the pid) from "the inventory failed while it lives" (throw, with stderr), and the tracker never overlaps samples so a slow lsof stretches the window rather than stacking subprocesses. The regression's degenerate-window refusals serve the same principle at the math layer: a test that never really sampled cannot evaluate its way to green.

**Why the churn row counts sockets twice.** The ±5 corridor is the criterion's own number and it bounds every handle at once; it would catch a per-cycle leak of any descriptor class (+100 minimum for a per-cycle socket leak against a corridor of ±5). The TCP inventory adds the zero-shaped oracle the criterion's "zero leaked sockets" names: after full churn the server holds exactly its listener and nothing else, asserted as a deep equality rather than a bound. The presence probe extends the same discipline to handles that never touch the FD table: a released session is gone from the live registry, proven by a probe session seeing only itself.

**Why raw HTTP cycles instead of 100 MCP children.** The criterion allows either. An MCP child per cycle would make the test measure Node process startup a hundred times; the churn the AC cares about is connection churn — sockets, sessions, registry rows — and four real `Connection: close` sockets per cycle against the real server exercises exactly that, at a rate where 100 cycles stay a bounded, deterministic second of wall time. The MCP-child path's reconnection behavior is Stories 2.1/2.2's proven ground; this story's subject is the descriptor/session floor under churn.
