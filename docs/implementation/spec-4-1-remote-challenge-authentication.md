## Intent

**Problem:** `docs/epics.md:434-445` (Story 4.1) requires the remote half of AD-5's one-session-mechanism-two-issuance-paths split: `/api/auth/challenge` issuing a single-use nonce (≥16 random bytes, 60 s expiry) and `/api/auth/answer` returning a session token for a valid signature, with replay resistance, the private key never leaving the installation, the FR-3 deletion rule, and NFR-3's no-authority-in-bodies negative mirrored at the wire. The substrate is ready and waiting: both routes sit frozen and UNREGISTERED in the route table (`server/api/routes.mjs:71-72` — `challenge` takes exactly `public_key`, `answer` exactly `nonce`+`signature`, so identity binds at challenge time and no key can be smuggled into the answer), the session registry is built as the shared issuer with its 12 h sliding TTL marked "provisional per DR-2, ratified at Story 4.1" (`server/api/session.mjs:13-14`), the installation keypair was born in Story 1.1 (`server/keys.mjs:160-171` — but `loadOrCreateKeypair` deliberately returns no private key, so the client cannot sign yet), and the Story 3.5 seam `AGENT_ROOM_CONNECTION_MODE=remote` (`server/client/api-client.mjs:86-90`) is a declared-only lane that has never carried a real credential — the trust matrix's remote lane is reachable, but its authentication is not. Meanwhile the server's only durable identity data is the chat_id_claims index; no enrollment record exists anywhere, so a challenge path would have nothing to gate against.

**Approach:** build the remote credential path around a durable enrollment record and the frozen routes, with one deliberate split: the challenge route is OPEN to any well-formed 32-byte public key (Story 4.2's invite enrollment itself runs "challenge-response" per `docs/epics.md:527` — enrollment needs nonces for not-yet-enrolled keys), while the answer route is GATED on enrollment: consume-first single-use nonce → Ed25519 verify over the raw nonce bytes against the challenge-recorded key → the new durable `enrolled_actors` table (additive store convergence, no schema-version bump — the `ensureChatIdClaimsTable` pattern, `server/store/room-log.mjs:625-627`) → session token from the SAME registry the local path uses. The only enrollment writer in this story is the existing Local Mode auto-enrollment: `POST /api/auth/local` now also records the presented key's fingerprint (zero wire change — reconnection re-proves possession instead of re-enrolling, FR-3/FR-12); Story 4.2's invite route joins as a second writer later. Client-side, `keys.mjs` gains two scoped helpers (`signWithInstallationKey` — the private PEM never leaves the module; `verifyWithRawPublicKey`), and the api-client's `authenticate()` branches on the connection mode: a declared-remote installation runs the challenge path — the first production use of the remote lane, exercising the 3.5 seam with real challenge-authenticated traffic exactly as the Epic 3 retro demanded (sprint-status.yaml action item `epic-3-retro-item-14`) — while the local lane keeps the token-file exchange byte-for-byte. DR-2 is resolved here by ratification: the 12 h sliding TTL stays as declared, validated against the reconnect cadence the substrate actually exhibits (see Design Notes). New constants (`CHALLENGE_NONCE_BYTES/TTL_MS/NONCES_MAX`, `CHALLENGE_SIGNATURE_MAX_CHARS`) and three new PUBLIC_ERRORS (`challenge_invalid` 401, `signature_invalid` 401, `not_enrolled` 403) join the single modules by name; the spine's AD-8 response vocabulary gains `nonce` with a dated amendment so the live-spine contract test stays green.

## Boundaries & Constraints

**Always:** keep the one-mechanism rule — the challenge path issues through the same `createSessionRegistry` instance, so sliding TTL, capacity, revocation, and verification behave identically to local-issued tokens (AD-5); bind identity at challenge time and verify the answer's signature against the challenge-recorded raw key only — the answer route's frozen field set (`nonce`, `signature`) admits no `public_key`, and the handler never reads one; consume the nonce BEFORE verifying the signature (a failed answer burns the nonce — no signature grinding against one challenge); keep the challenge route open to unenrolled keys (Story 4.2's enrollment is a challenge-response consumer) and the answer route gated on the durable `enrolled_actors` record; add the enrollment table through the additive open-path convergence (IF NOT EXISTS + column verification + the STRICT verification list at `server/store/room-log.mjs:561`) with NO `user_version` bump; seed enrollments only from the existing local exchange's success path — a rejected local exchange still writes nothing; keep nonces in memory (connection-time state — a server restart invalidates outstanding challenges, the durable enrollment survives, and the ephemeral/ durable split of AD-6 holds); import every new bound by name from `server/constants.mjs` and register the three new codes once each in `PUBLIC_ERRORS`/`PUBLIC_ERROR_STATUS`; keep the private key file-scoped inside `keys.mjs` — signing reads the PEM, returns only the signature, and no return value, log line, wire body, or tool result ever carries key material; make the declared-remote branch never fall back to the local token file (a declared-remote installation has declared the OS-user boundary is not its own); record the earned `transport: 'remote'` only after a successful challenge exchange so the trust matrix's input stays an authentication fact, never a claim; amend the spine additively with dated notes and keep `parseAd8Vocabulary` green — the AD-8 amendment prose must carry no backticks except `nonce` itself (every backticked token in the responses segment is extracted as a response field name, `tests/api-contract.test.mjs:77-88`); keep every rejection zero-state (no enrollment write, no claim touch, no nonce resurrection); test against real spawned server children and the real api-client in the house style, with an injectable clock for the 60 s expiry and the sliding TTL.

**Block If:** a replayed answer request ever yields a session token — halt; replay resistance is the story's spine. An answer whose signature verifies against a key OTHER than the one the nonce was issued to — halt; identity bound at challenge is the anti-smuggling property. The answer route succeeds for a key with no `enrolled_actors` row — halt; the gate is what keeps Story 4.2's invite semantics additive. Any private-key byte appears in a request body, a response, stderr, or a tool result — halt; FR-3's first consequence. The local lane's behavior changes on the wire (different request, response, or rejection shape) — halt; Local Mode must not regress (FR-1's friction rule). A rejected request writes enrollment, claims, or a session — halt; AD-7's zero-state invariant. The session token's TTL, entropy, or registry diverges from the local path's — halt; two session mechanisms is exactly the drift AD-5 forbids. A limit literal or an error status appears outside the constants module — halt; AD-9's single-source rule. The client's declared-remote branch presents the local token file under any circumstance — halt; the declaration's meaning dies with the first fallback.

**Never:** do not implement or un-stub `POST /api/auth/enroll` (Story 4.2's route — it stays 404-unregistered here, and `tests/api-host.test.mjs:606` narrows to pin only `enroll`); do not add, rename, or re-class any route or request field (the table and request vocabulary are already exactly right — additions only, and none are needed); do not add a configured server URL, HTTPS transport, or remote bootstrap to the client (Story 4.3's; the challenge lane in this story runs against the loopback server through `ensureServer` exactly like today — what changes is only the credential discipline); do not touch the trust matrix's cells, the MCP tool schemas, or the viewer; do not persist nonces, sessions, or challenge state to SQLite; do not change `SESSION_TTL_SECONDS` (DR-2 is ratified as declared, not retuned); do not restate the fingerprint definition (Epic 1 retro item 2 collapsed it into `server/constants.mjs` — import `FINGERPRINT_PATTERN`/`fingerprintFromPublicKey`); do not edit `docs/epics.md` (the DR-2 resolution is recorded in this spec and the spine's Open Question 1, not by rewriting the register); do not skip, `.only`, or todo anything; do not claim Story 4.2's invite flow, Story 4.3's transport policy, or cross-machine deployment as proven.

  5. **MEDIUM (luna-4)** — the four challenge bounds (nonce bytes ≥ 16, 60 s expiry, single use, canonical signature) had no independent literal oracle: the suites derived expectations from the imported constants and would have adapted silently to drift. ## Design Notes

- **Why the challenge is open and the answer is gated.** AD-5's shape — "Enrollment (invite-gated, atomic, per FR-14) registers the public key once; reconnects re-prove it" — needs a possession-proof primitive that works for keys NO ONE has enrolled yet, or Story 4.2's invite enrollment cannot prove possession via challenge-response (`docs/epics.md:527`: "enroll A (challenge-response)"). Issuing a nonce is privilegeless: it is a random value bound to a key shape. Minting a session is the privilege, and that is exactly where the `enrolled_actors` gate sits. This keeps 4.2 purely additive: it adds a second WRITER to a store this story built and read-gated, and changes nothing about the routes it lands between.
- **Why identity binds at challenge time.** The frozen route table already made the decision (`server/api/routes.mjs:72` — answer's fields are `nonce`+`signature`, no `public_key`); this story implements its consequence. A captured challenge can be answered only by the key it was issued to, and a man-in-the-middle cannot substitute a key at answer time — there is no field to substitute with. Row 4 proves the property, row 13 proves the frozen field set rejects the smuggling attempt outright.
- **Why consume-before-verify.** A verify-then-consume order would let one nonce absorb unlimited signature guesses for its 60 s lifetime. Ed25519 forgeries are ~2^248 work, so the ordering is not load-bearing against brute force — but it is free, strictly safer, and makes "single-use" mean single-use unconditionally (row 6). The same order makes replay resistance trivial: the first answer, whatever its outcome, kills the nonce.
- **Why nonces stay in memory while enrollment goes to SQLite.** A nonce is connection-time state with a 60 s life — persisting it would buy nothing and survive exactly the crashes it should not (a restarted server's outstanding challenges MUST die; that is the safe direction). Enrollment is the opposite: FR-3/FR-12 require reconnects to re-prove WITHOUT re-enrolling, so the registration survives restart. This is AD-6's ephemeral/durable split applied to the auth surface, and it makes row 8's restart half a feature, not a caveat.
- **Why the local exchange seeds enrollment.** Local Mode auto-enrollment already admits the presented key under the OS-user boundary; recording it turns an implicit fact into the durable record the challenge gate reads, with zero wire change and zero new privilege (the local token remains the bootstrap credential). It also gives this story's tests an honest, shipped enrollment path — no test-only seeding backdoor.
- **Why the declared seam is the auth-path switch, and why no fallback.** In 4.1 there is still no configured server URL (Story 4.3), so "which credential discipline applies" has exactly one honest source: the installation's declared connection mode — the input Story 3.5 already shipped as strictly fail-closed and the Epic 3 retro explicitly reserved for this use (`epic-3-retro-item-14`). A declared-remote installation has asserted the OS-user boundary is not its own; presenting the shared local token would contradict the declaration and silently widen the credential's reach, so the branch never falls back — coded failures surface (row 10). When 4.3 adds configured URLs, the switch gains a second, configuration-driven trigger; the declaration remains.
- **Why DR-2 ratifies at 12 h sliding rather than retuning.** The registry is in-memory: a server restart invalidates every session regardless of TTL, and restarts dominate the reconnect cadence the substrate actually exercises (the 2.4 churn cycles, the 2.5 kill/restore drill, the client's ECONNREFUSED recovery loop — all re-auth through the single-flight `authenticateOnce`). For idle expiry, the sliding refresh means any session used within 12 h never re-auths, and one that does re-auths transparently with no human action — so a shorter TTL buys no security (the bearer token's exposure window is its lifetime either way, and recovery is already replay-resistant) and costs nothing to avoid. The 12 h sliding TTL stands exactly as AD-9 declared it; Open Question 1 closes with that record.
- **Why the spine amendment is load-bearing, not decorative.** `tests/api-contract.test.mjs` parses the LIVE spine document and pins `RESPONSE_FIELD_VOCABULARY` against the AD-8 responses segment (`:84-88`) — and every backticked token in that segment is extracted as a field name. The `{nonce}` response therefore requires the dated amendment to keep the suite green, and the amendment's prose must stay backtick-free except for `nonce` itself. This is the same mechanism Story 1.4 used for `session_token`.
