## Intent

**Problem:** `docs/epics.md:472-482` (Story 4.4) requires Epic 4's server gates: four independently testable rate gates with idempotency ordered first, and the complete FR-17 send-status set. The substrate left by earlier stories is exactly the reserved seams — the budgets stage is a pass-through except the 4.2 enroll limiter (`server/api/pipeline.mjs`), the store's `appendMessage` already owns the idempotency tuple but has no duplicate gate, `SEND_STATUSES` in the constants module carries only two of the six FR-17 statuses, `rate_limited` exists as a code but carries no retry delay, and NFR-5's send p95 ≤ 150 ms is a declared number with no executable check (the epic's own wording defers that to this story, docs/epics.md:207). Nothing throttles abuse, a duplicate send has no named outcome, and a rate-limited sender is not told when to retry.

**Approach:** four gates over three layers, each importable, injectable, and isolated. (1) **The request budget** — a token bucket per Actor fingerprint (sustained REQUEST_BUDGET_PER_MINUTE, burst REQUEST_BUDGET_BURST), living in the budgets stage (AD-7: never in a handler), consuming one token for EVERY authenticated (actor-class) request at admission — failed and replayed attempts included; a long-poll is one HTTP request and counts once, at admission, never per poll iteration. (2) **The send bucket** — the same token-bucket arithmetic at SEND_TOKEN_REFILL_PER_SECOND/SEND_TOKEN_CAPACITY, scoped to the send route, and IDEMPOTENCY-AWARE: before the bucket consumes, the stage probes the store's idempotency index (`findIdempotentSend`, a pure read of the (room, actor, client_message_id) tuple), so an exact retry is admitted free and consumes nothing even from an empty bucket — the AC's "exact retries return the original and consume nothing" holds during a rate-limited period, and the bucket spends tokens only on NEW sends. (3) **The duplicate gate** — inside the store's single append transaction, ordered AFTER the idempotency lookup (the ordering is structural, not conventional: a retry short-circuits at the tuple and can never reach the gate), comparing (actor, room, text, reply_to_seq) over DUPLICATE_WINDOW_MS with the reply context in the tuple; a hit answers duplicateDropped with the original message and writes nothing. Because the check runs inside BEGIN IMMEDIATE, two racing same-text sends serialize: exactly one commits, the other is dropped. (4) **The idempotency tuple** itself was already first in the store; this story makes it first at the GATE too (the probe) and pins both orderings by test. Refusals answer the coded `rate_limited` (429) whose error envelope carries the NEW declared extra `retry_after_ms` (the gate computes the ceil of one token's refill time); the duplicate drop answers a normal 200 result `{status: 'duplicate_dropped', original_seq, room_id}`. `SEND_STATUSES` completes to the FR-17 six (committed, rate_limited, duplicate_dropped, storage_low, client_message_id_conflict, banned) with the last two wired by name and triggered by Stories 4.5/4.6. All five limit values are the constants module's, imported by name, operator-tunable as abuse floors (never a DoS guarantee) through startServer overrides and — for the direct launch the harnesses spawn — five strictly-validated AGENT_ROOM_ env knobs. NFR-5 becomes executable: a dedicated perf test drives a warm in-process server over real loopback HTTP and asserts the end-to-end send p95 ≤ 150 ms — an upper bound that includes the loopback round trip, so server-side processing is within 150 ms a fortiori.

## Boundaries & Constraints

**Always:** keep gate logic in the budgets stage and the store — a handler never gates (AD-7's tested invariant); check the idempotency tuple before the duplicate gate and before bucket consumption (the probe), so a retry is never punished and never dropped; count every authenticated request at admission whatever it later answers (failed, replayed, long-polled once); make every refusal name its delay (rate_limited + retry_after_ms via the declared extras allowlist — a code carries only its declared extras); make duplicate_dropped a 200 result naming original_seq with the store byte-untouched, never an error and never a silent success; keep the reply context and the room inside the duplicate tuple (identical text in a different room or reply context is a different operation); import all five limits by name from the constants module (AD-9 — no restated numbers anywhere); validate operator overrides at startup and env values per-knob with a warning fallback, never blocking a boot; key both buckets by the token-derived actor fingerprint (identity from the session, NFR-3); sweep expired bucket state lazily (an entry idle past a full refill horizon is provably full — dropping it equals refilling it, so the maps hold only live keys); test each gate in isolation with an injectable clock, and the p95 over a warm server.

**Block If:** a send's duplicate gate fires for an exact retry (same client_message_id) — halt; the tuple owns it. A rate_limited refusal without a positive retry_after_ms — halt; FR-17. A duplicate_dropped that writes a row, answers an error status, or omits original_seq — halt. A retry refused by the send bucket — halt; the probe runs before consumption. Identical text deduplicated across rooms or reply contexts — halt; FR-16's own carve-out. A limit literal appearing outside the constants module — halt; AD-9. A refusal answered from a handler instead of a stage — halt; AD-7. Two racing same-text sends both committing inside the window — halt; the single writer serializes them.

**Never:** do not implement bans or storage admission (4.5/4.6 wire the banned/storage_low names themselves — the enum is complete, the triggers are theirs); do not budget pre-auth routes per key (they have no key — the enroll limiter keeps its per-identity scope, and AD-7's global pre-auth floor stays unowned); do not gate viewer or health routes (no Actor budget applies); do not refund consumed tokens on later failure (the budget counts attempts); do not let the duplicate gate compare chat ids (attribution is not identity — the tuple is actor, room, text, reply context); do not bump the schema version (the gate is stateless in-process arithmetic + a SELECT inside the existing transaction); do not skip, `.only`, or todo anything; do not commit.

(1) **The duplicate gate lives in the store's append transaction, ordered after the idempotency lookup** — making the AC's gate ordering structural rather than conventional (a retry short-circuits at the tuple and cannot reach the gate), giving the drop the single writer's race safety (two concurrent same-text sends serialize: exactly one commits), and keeping "the store is untouched" literally true. ## Design Notes

- **Why the gates live where they live.** AD-7 fixes the pipeline order (protocol → transport → auth → budgets → authz → handler) and the tested invariant that handlers contain no gate logic. The two token buckets are admission control over requests — budgets-stage work. The duplicate gate is content policy over a durable write whose correctness depends on serialization — store work, inside the one BEGIN IMMEDIATE the append already runs. Splitting them any other way either puts content policy behind a handler (banned) or makes the ordering a convention two files must agree on (violable). Here the ordering is enforced by construction: the store checks the tuple first, and the gate probes the same tuple before spending anything.
- **Why the send bucket probes the store instead of keeping its own admission memory.** A "seen triples" ledger at the gate would need a TTL (how long is a retry?), would disagree with the store after a restart (the store remembers committed sends; a gate memory would not), and could be defeated by the very crashes the outcome-unknown discipline exists for. The store's UNIQUE index answers in one indexed SELECT with perfect recall: if the tuple exists, whatever the payload, the send's outcome is already determined (original or coded conflict) — no new message can commit, so nothing should be consumed. The probe runs before the bucket; a rate-limited period therefore never punishes a retry.
- **Why the request budget consumes before the field read (on the send route, in-stage) and before everything except protocol/transport/auth everywhere.** The AC says the budget counts EVERY authenticated request, failed and replayed included. A request that dies at shape validation is still a request the server did work for — and the one dodge the budget exists to close is exactly "send garbage that fails somewhere and never spend your budget". On the send route the field read happens inside the budgets stage (after the request budget consumes, before the send-bucket probe — the probe needs the body's client_message_id); everywhere else it stays after the stages as before, via the re-entrancy flag. Either way a send route request consumes its budget token before it can be refused for shape.
- **Why rate_limited carries retry_after_ms as an envelope extra, not a header.** AD-8's error envelope is the frozen contract, and Story 1.7 built the declared-extras mechanism (`ERROR_ENVELOPE_EXTRAS`) for exactly this growth: a code may carry only the extras it declares, picked by name, unable to clobber the fixed fields. The machine-readable delay travels the same authenticated JSON channel as the rest of the contract; the spine amendment declares `retry_after_ms` in the response vocabulary, and the contract test pins the allowlist so nothing else can ride along.
- **Why duplicate_dropped is a 200 result and not an error.** FR-17's statuses are the sender's actionable notices; a dropped duplicate is not a failure of the request — it is the server saying "this exact operation already committed at seq N, name-your-reason, nothing more to do". An error shape would push clients into retry loops against a permanent condition; a 200 result with `status` and `original_seq` resolves it in one round trip and keeps the outcome-unknown discipline untouched (retries of the SAME id never see this path at all — they short-circuit at the tuple to the original committed message).
- **Why the operator surface is startServer overrides plus five env knobs.** The AC demands operator-tunable floors; the ratified env convention (AGENT_ROOM_CLAIMS_TTL_MS, AGENT_ROOM_PRESENCE_TTL_MS) already exists for the direct launch. The harnesses spawn that launch, and their workloads (hundreds of cycles from one key, 800-message warmup rounds) are exactly the "churn-like legitimate load" an operator raises floors for — so the harnesses set the documented env rather than stubbing or pacing, the gates still execute on every request, and every refusal behavior is tested at the declared defaults in the new suite. Junk env values warn and fall back; junk startServer values fail startup; neither path restates a number.
- **Why the memory row's warmup grew.** The fixed warmup exists to drive the allocator past its ramp so the measured slope reads leaks, not growth (Story 2.4's warm-then-measure discipline). Story 4.4 widens each cycle from four to six requests and adds a durable append, so the ramp is longer; 2500 cycles stopped reaching the plateau (measured: a 6.4%/s slope that vanished at 4500). The change is the harness keeping its own oracle honest, not the rule loosening — the tolerance stays 2%.
