## Intent

**Problem:** `docs/epics.md:332-342` closes Epic 2's continuity arc with the one-time upgrade: a v0.1 user's existing local data must be upgraded in place so Local Mode continuity carries into v0.2. The mechanics are pinned by AR-4 (`docs/epics.md:88`): absorb **or stop** any live v0.1 daemon first (pid from runtime.json), then a single `BEGIN IMMEDIATE` transaction — detect (`user_version`) → per-room re-sequencing + `reply_to_seq` remap → stamp v2 — idempotent on crash, with the one-time documented cursor reset belonging to this upgrade only. The third criterion binds the outcome: reply threads intact, room-local sequences contiguous from 1, and the realm_id **preserved** — an in-place migration is the same realm with the same trust; only moving to a new server/host creates a new realm (the AR-14 boundary made explicit). Nothing implements any of this: the v0.2 store **refuses** a v1 file (`server/store/room-log.mjs:431-436` and the createSchema twin — `database_schema_unsupported`, byte-untouched), and the design intent recorded at `server/store/room-log.mjs:13-14` ("Epic 2 owns migration") has an owner but no code. A v0.1 user upgrading today gets a hard refusal at boot.

**Approach:** one new production module, `server/store/migrate-v1.mjs`, exporting `migrateV1InPlace({ dataDir })`, wired into `startServer` (the one production caller of `openRoomLog`) so a v1 file migrates automatically at boot instead of refusing. The module runs the pinned ordering: an absorb-or-stop phase that reads `runtime.json` and stops (SIGTERM → bounded wait → SIGKILL) only a process the record names AND whose `/health` answers like an agent-room server — accepting both the v0.1 response shape (`{ok, version}`) and the v0.2 shape (`{ok, result:{version}}`), since the daemon being identified is the v0.1 one; then one `BEGIN IMMEDIATE` transaction that re-detects the version inside the lock, re-sequences every room's messages from 1 in arrival order (ascending global seq), remaps each `reply_to_seq` from global to room-local through that per-room map, reshapes the schema to the five v2 tables (built from `room-log.mjs`'s now-exported DDL builders, so both paths construct byte-identical tables), mints the realm's first id, verifies integrity (`foreign_key_check`, FK target set, per-room contiguity) before the stamp, and stamps `user_version = 2` — the stamp itself transactional, which is what makes a crash mid-migration resume as a plain rerun on the untouched v1 file. Plus its proof: `tests/migration.test.mjs` in the house style (hand-crafted real v1 databases with global interleaved sequences and same-room reply chains, literal migrated-shape oracles, real child processes for the daemon-absorb and mid-migration-SIGKILL rows, read-only SQLite inspection), and the filled 2.3 entry in the AC evidence file.

## Boundaries & Constraints

**Always:** run absorb-or-stop BEFORE the migration transaction touches the database, and signal only a positively-identified process — the record's pid alive AND a bounded `/health` probe on the recorded port answering agent-room (either generation's shape); stop it SIGTERM, bounded wait (`SERVER_CHILD_REAP_TIMEOUT_MS` per signal), then SIGKILL, and fail the migration before the database opens if a positively-identified daemon survives the kill window; reclaim a dead-and-unreachable record silently; refuse coded (`server_port_conflict`, mirroring ensure-server's rule) when the recorded port is held by a live process that answers but is NOT agent-room — a foreign process is never signalled; proceed without signalling when a recorded live pid never answers (unidentifiable — it may not be the daemon; SQLite's single-writer transaction arbitrates instead); run the whole reshape inside ONE `BEGIN IMMEDIATE` transaction whose first act is the authoritative in-lock version re-detect (a concurrent boot's completed migration is a no-op, never a second remap); copy messages per room in ascending global-seq order so every reply meets its (earlier, same-room) target before it needs the remap, failing coded on a reply whose target is missing or not earlier; derive each message's `actor_fingerprint` deterministically as SHA-256 over the v1 actor id and map each send-time display name into the DR-1 grammar (non-grammar characters → `_`, truncate to `CHAT_ID_MAX`); migrate every v0.1 room as `kind='broadcast'` with `pair_key` NULL and a NULL creator, preserving ids, titles, and created_at verbatim; mint the realm's first id inside the transaction (a UUID, as every first boot does) so only a COMMITTED mint ever exists; verify before the stamp — `PRAGMA foreign_key_check` empty, the messages table referencing exactly `rooms` and `messages`, every room's sequences contiguous from 1 — then stamp `user_version = 2` inside the same transaction; build every v2 table from the DDL builders exported by `room-log.mjs` (extracted from `createSchema`/`ensureRealmTable`/`ensureChatIdClaimsTable` without changing their text) so the migration and the fresh-schema path cannot drift; treat the probe as probe-before-touch — an absent, symlinked, irregular, corrupt, or non-v1 file is `{migrated: false}` with no write of any kind, leaving `openRoomLog`'s refusal paths (future versions, version-0 files with foreign tables, corrupt files, and the v1 refusal on the raw store path) exactly as they were; document the one-time cursor reset in exactly one production place (the migration module's header) plus this spec, and nowhere else. **Block If:** the migration cannot preserve reply threads, room-local contiguity from 1, or realm stability across a restart — halt with the SQLite rows; that is a durability defect in the migration, not a test correction. Making the store's raw open path migrate (mutating a schema it does not own, or breaking the byte-untouched refusal invariant) is a design violation — halt; the store must refuse every foreign schema and the startup must own the upgrade. Killing a process that did not positively identify as agent-room is a Block If — the absorb-or-stop's false-positive kill discipline is absolute. A migration failure that leaves anything partial on disk (a `*_next` remnant, a half-populated table, a stamped version on un-reshaped data) is a transactionality defect — halt. SIGKILL/recovery proves flaky across repeated runs — halt with the failing run rather than retry-until-green. **Never:** do not modify the retired v0.1 files (`server/database.mjs`, `server/roomd.mjs`, `server/daemon-client.mjs`) — they are the read-only reference for the v1 shape and, in the daemon tests, the behavior being absorbed; do not seed `chat_id_claims` from v0.1 actors (the derived fingerprint is not the key the upgraded agent will present — offline addressing against it would resolve to a stale identity); do not fabricate room creators (v2 never fabricates an identity for a broadcast room); do not promise DM continuity across the migration (v0.1 had no DMs and no fingerprints to key them with — recorded honestly in the mapping decisions); do not migrate or consult any legacy client cursor file (the reset is structural: the new realm key takes every pre-upgrade cursor value out of service, and clients resume from `after_seq` 0); do not restate a limit literal outside `server/constants.mjs` (the new settle knob is declared there; the stop-wait reuses `SERVER_CHILD_REAP_TIMEOUT_MS`'s identical semantic); do not change the frozen route table, the wire contract, or any Epic-1 behavior; do not weaken, skip, or `.only` any test, and do not soften a rollback or no-op oracle to get green.

The store open path is synchronous; absorb-or-stop is irreducibly asynchronous (an HTTP health probe and bounded process waits), and `openRoomLog` has exactly one production caller — `startServer`. The migration therefore wires there, and the store's probe-before-touch refusal stays as defense in depth: the raw store never mutates a schema it does not own, refused files stay byte-for-byte untouched (a tested invariant this story explicitly preserves), and every non-v1 refusal keeps its code. A v1 file at BOOT is migrated — which is the AC's own frame ("at startup, when the server boots").
- **Recorded decision — the health probe accepts both generations.** `ensure-server.mjs`'s `probeHealth` accepts only the v0.2 shape, because it gates attach to a v0.2 server. The migration must recognize the v0.1 daemon it is about to stop, whose `/health` answers `{ok, version, protocolVersion}` (`roomd.mjs:277-280`) and whose record carries the port inside `httpOrigin` rather than a `port` field. The migration ships its own bounded, size-capped probe accepting either shape; identification is the conjunction of the record's live pid and that probe.
- **Recorded decision — the kill discipline is positive-identification only.** Exactly one condition ever leads to a signal: the record names a live pid AND the recorded port's `/health` answers agent-room (either generation). A dead pid is reclaimed silently (the AC's "dead-and-unreachable entry"); a live pid whose port cleanly answers non-agent-room is a coded `server_port_conflict` refusal (ensure-server's rule, mirrored — a foreign process is never signalled); a live pid whose port never answers is unidentifiable (it may not be the daemon — pid reuse is realistic over a v0.1 era measured in months), so after one bounded settle window the migration proceeds WITHOUT signalling and lets the single-writer transaction arbitrate. False-positive kills are impossible by construction; the false-negative case degrades to SQLite's own serialization, which is already a coded path.
- **Recorded decision — the realm_id is minted fresh inside the migration transaction.** The v0.1 file has no realm id, so "preserved" cannot mean an id carried over; it means the REALM continues — same file, same history, same trust — and the minted id is stable from the committing boot forward (proven across restarts). The mint lives inside the single transaction, so a crash rolls it back and the resume mints again; only a COMMITTED mint ever exists, and the SIGKILL test compares resumed state against a reference migration masking only the per-migration mint (id + timestamp), everything else exact.
- **Recorded decision — all v0.1 rooms become broadcast rooms; DM continuity is not promised.** v0.2 pair keys need Ed25519 fingerprints; v0.1 actor ids are identifier strings (`agent:<uuid>`), not keys. Migrating every room as `kind='broadcast'` with implicit membership preserves what v0.1 actually guaranteed — its own read path (`readRoomMessages`) checked only room existence, so every migrated commons room stays readable and writable by every Actor — and honestly declines what v0.1 never had. Multiple migrated broadcast rooms are within the v2 model: `findBroadcastRoom` deterministically picks the oldest as THE Broadcast Room and the rest remain open commons rooms.
- **Recorded decision — attribution mapping is deterministic and documented: fingerprints derived, chat ids grammar-mapped, claims NOT seeded.** Message `actor_fingerprint` is SHA-256 over the v1 actor id (stable, distinct, but NOT the key the upgraded agent will present — v0.1 had no keys, so live identity begins with the v0.2 keypair; history attributes faithfully). Message `chat_id` maps the send-time display name into the DR-1 grammar (non-grammar characters → `_`, truncate to `CHAT_ID_MAX` — the truncation is required by the v2 CHECK, which v0.1's 80-char names would violate). `chat_id_claims` stays empty: seeding it would let `room_direct_open` resolve an old name to a fingerprint the agent no longer holds — worse than an honest `chat_id_not_found` that resolves on reconnect.
- **Recorded decision — the cursor reset is structural, and documented exactly once.** Client cursors live under `PLUGIN_DATA/realms/<realm_id>/`; the migration mints the realm's first id, so every pre-upgrade cursor value is outside the new realm key and never consulted, while room-local v2 sequences start from 1 where v0.1 sequences were global. No legacy cursor file is read, rewritten, or migrated. The single production documentation site is the migration module's header (asserted by a scan test); this spec is the second and last statement of it.
- **Recorded decision — the resume oracle is a reference comparison.** A migration transaction is opaque to outside observers until COMMIT (uncommitted DDL is invisible, `user_version` flips only at the stamp), so a mid-transaction SIGKILL cannot be synchronized by polling. The kill test sizes the fixture so the migration vastly outlasts the kill delay, asserts the pre-boot state (still v1, all rows) whenever the kill is shown to precede completion, and proves the resume by comparing the completed migration against a reference migration of a pristine copy of the same fixture — with the deterministic mid-transaction-failure rollback proof (bytes included) carrying the sharp transactionality claim.

## Design Notes

**Why one transaction is the whole idempotency story.** The migration's crash safety does not come from checkpoints, markers, or multi-phase bookkeeping — it comes from SQLite. Every effect of the upgrade (the re-sequenced copies, the rename swap, the drops, the realm mint, and the `user_version` stamp, which lives in the database header and is written transactionally) is either fully committed or not at all. A crash mid-flight therefore leaves a byte-clean v1 file whose next boot reruns the identical transaction from the start; "resume" is not a state machine, it is the same single step tried again. That is also why the in-lock re-detect is the authoritative version check: a concurrent boot that committed first makes every loser's transaction a no-op rather than a second remap, and the no-op oracle (three consecutive runs, one of them a full server boot, all state deep-equal) converts that property into executable proof. The stamp's transactionality is not assumed — the rollback test reads the version AND the bytes after a deliberately induced mid-copy failure and requires both untouched.

**Why absorb-or-stop runs before the database opens, and why it signals so rarely.** The v0.1 daemon holds the database open and can write v1 rows into it; migrating underneath a live writer would be a race wearing a transaction's clothes. Stopping the daemon first — identified by the record's live pid plus an agent-room health answer — makes the window honest: after the stop, the migration's `BEGIN IMMEDIATE` is uncontended by anything that owns the old schema. The rare-signal discipline is the same principle ensure-server applies to attach: a process is killed only when the evidence names it as ours (live recorded pid AND an agent-room `/health`), because the alternative — killing by pid alone — turns pid reuse into data loss. Every non-confirming case has a non-violent path: dead means reclaimed, foreign means refused coded, silent means proceed under SQLite's own write serialization.

**Why the store still refuses, and why that is not a gap.** The migration's wiring is the boot, and the boot is the only production path that opens the store. Leaving `openRoomLog`'s refusal in place preserves a tested invariant this codebase paid for in Story 1.2 (probe-before-touch: a refused file's bytes are never modified) and keeps the failure mode honest if any future caller opens the store directly against a v1 file: a coded refusal with a message naming the startup migration, not a silent half-upgrade by a layer with no daemon-absorption discipline. The refusal's message changed (it may no longer claim migration is unsupported); its code, its byte-untouched behavior, and its tests did not.

**Why the mapping decisions lean deterministic.** Every derived value in the migration (fingerprint from actor id, chat id from display name) is a pure function of the v1 data, so the migration is idempotent not just at the file level but at the value level: two migrations of the same v1 file produce identical maps. That is what lets the SIGKILL test compare a resumed migration against a reference migration row-for-row and fail on any drift beyond the two values that are genuinely per-completion (the realm's minted id and its creation timestamp). Determinism is also the honesty guarantee: nothing in the migrated history depends on when or how many times the upgrade ran.

**Why claims stay empty and why that is continuity, not loss.** The v0.2 offline-addressing index exists so `room_direct_open` can resolve a Chat ID to a KEY. The migration can derive a name-shaped string and an id-shaped fingerprint, but the key those would point at does not exist — the upgraded agent will present a different fingerprint the moment it reconnects. Seeding the index would convert a missing peer into a wrongly-addressed room. Leaving it empty means the first post-upgrade reconnect re-claims the name against the live key, and addressing works from evidence rather than from a guess the migration declined to make.
