## What was blocking, and what I did about it

The first attempt at each call failed with `chat_id_taken`: *this* Chat ID (`ZCODE-MAC-2`) was held by another connected session, so no room could be opened at all — every room tool, even read-only ones like `room_presence` and `room_status`, failed at the identity layer.

The cause was not a foreign agent. I traced it:

- This installation is in **remote mode** (`remote-config.json` → `https://43.229.78.103:18444`, the staging server), and its key is `sha256:9c7848eb…c94e7`.
- The staging server's presence showed `online: []` — no live session anywhere — yet the bind was still refused. That's the gap between the 180-second presence TTL and the 12-hour session lease: a row silent for minutes is invisible in presence but still squats the name.
- `ZCODE-MAC-2` is configured in exactly one client on this machine, `.vendor-lab/rel1-zcode` (my own installation), and `/tmp/rel1-64-phaseA.log` shows the scripted **Phase A** run at 18:03 used that same client, then exited without releasing its session. Its dead row was the holder.

I took the name back with the repo's own designed recovery path — `agent-room session replace`, which reported `replaced: true, released: true` (the server independently only ever displaces a *same-Actor* session, so a foreign holder was never at risk). The first attempt was declined because the piped confirmation landed before the prompt existed (`confirm_declined`, nothing taken over); re-running with the answer delayed succeeded.

One thing worth flagging for the demo: Phase A hit `ambiguous_chat_id` because `CLAUDE-STAGING-1` was claimed by two actors, and it picked `fd512406…f425` (CLAUDE-**MAC**-1) on recency alone — its own log notes that wasn't confirmed to be the staging instance. This run passed the explicit `target_fingerprint` `d371a6d7…c259c`, so it targeted the staging-machine Claude Code directly and did not depend on that guess.

## The blocker and how I cleared it

All three calls returned the same coded error:

```
chat_id_taken: This Chat ID ("ZCODE-MAC-2") is held by another connected session.
```

Diagnosis: my MCP client (`PLUGIN_DATA=.vendor-lab/rel1-zcode`, remote mode → `https://43.229.78.103:18444`) authenticates as Actor `sha256:9c7848eb…`, and the stale holder of `ZCODE-MAC-2` was **the same Actor** — an earlier phase of this REL-1 run whose process exited without releasing the name. Evidence it was dead: only one agent-room MCP client process existed on the machine (mine, PID 73826); presence did not list `ZCODE-MAC-2` at all (silent past the presence TTL, row still alive); the last message under that name was 11:16:28Z, before this phase started. The automatic re-auth recovery never fires because the dead holder's *token* was still live, so the lease (12 h) kept the name.

I used the one sanctioned takeover — `agent-room session replace` (operator-authorized, same-Actor only):

```json
{"ok":true,"command":"session replace","chat_id":"ZCODE-MAC-2","mode":"remote",
 "server_url":"https://43.229.78.103:18444","fingerprint":"sha256:9c7848eb…",
 "replaced":true,"released":true,
 "note":"the name is free until the live client binds it again; restart the client that uses this Chat ID"}
```

The live client re-bound `ZCODE-MAC-2` on its next call. Nothing else was displaced — no other agent was touched.
